# Invariants: The Workshop: orders, products, stock

Full text of the rules that [`CLAUDE.md`](../../../CLAUDE.md) keeps in short form, with the reasons and the history behind them. `Vault:` pointers name notes in the maintainer's private knowledge base; everything a contributor needs is here.

## The Workshop's rights are four domains and one filing right, asked in one place (WS-13 E13 §O, m194)

Sixteen permissions — `orders:read/create/update/delete/file_prints`, `products:read/create/update/delete`, `customers:read/create/update/delete`, `stock:read/move/adjust`; `projects:*` and `stock:manage` are gone, with no runtime fallback (the group editor refuses the old keys). m194 maps them; m046's `_CARRIED_FORWARD` keeps the four `projects:*` keys alive until m194 runs — the owner's one exception to frozen migrations (N14), never a precedent. Filing a PAST print is `F(print)` = `orders:file_prints` ∨ (`orders:update` ∧ that print's `archives:update_all` / `update_own`); NEW work under an order (print dialog, queue, reprint, clone, the plate's «Repeat», Telegram) is `Fф` = `orders:file_prints` ∨ `orders:update`. Both are answered by `api/routes/_workshop_rights.py` (`ensure_may_file`, `ensure_may_file_future`, `may_file_future`) and the link itself by `order_filing.resolve_link` (an open order, else 409 `order_closed`; a line of that order); a copy for someone without `Fф` goes `without_order` / `keep_order=false`, and the button says so before it is sent. Never hand Operators `archives:update_all` for filing — it opens everybody's photos and files (upstream security #5). Past prints move through the order's commands (`add-archives` / `remove-archives`; `PATCH /archives` keeps its binding fields under the same checks), and every exit locks the order rows, then the print, then the parts' ledger (lock class PRINT, `archive_write_scope(first=…)`, `lock_prints`): C1 — a print whose output the order received never leaves — is read under the order's lock, and a print in the trash is refused whole-batch (409 `print_in_trash`), never filed and never skipped. A write that changes the Workshop from another section asks that domain's own write too, through `core/auth.RequestCredentials` (`request_credentials` + `creds.check(gate)`, which honours an API key's scope, never a hand-written permission test): linking or unlinking files and folders to products, and a move that changes a file's set of products (compared before anything moves; a batch with one such file is 403 and nothing moves), ask `products:update`. Taking from stock (explicit numbers, `auto`, «Take from stock») is `stock:move`; the consequences of an order edit (release on cancel, completion, a lower quantity) need no stock right; write-offs are `stock:adjust`; a delete asks the rights of its real consequences (O24). Reads are masks, not page gates: `workshop_view()` — bound per request by `bind_workshop_credentials` on every router that reads it — nulls another domain's fields, and a filter or sort on a hidden field is 403 `workshop_read_required`; `customers:read` sits in the `can_manage_projects` key bucket (contacts are personal data); a dispatch note's recipient snapshot needs `customers:read` ∨ `stock:move`, else a minimal row and 403 `dispatch_note_restricted`. A file an order names (`from-files`, a plate line) must be visible through `library_name_scope` + `file_name_visible`; someone else's and a missing one are the same 404. A folder's link to products is a standing rule its linker set: a file that lands in it (upload, slice, ZIP) inherits the link, and deleting the folder drops it, without asking `products:update` (owner, 2026-10-04). The UI only hides or explains the doors — one function per action in `utils/workshopRights.ts`, and `SectionLink`: a name into a section you cannot read is text, an action is absent. Vault: `40-invariants/inv-workshop-rights-by-domain.md`.

## In the Workshop the server counts, sorts, searches and pages (WS-01, 2026-09-25)

Every figure and every list of the Projects section — orders, products, customers, stock, and what the workshop redesign adds — arrives finished from the backend: coverage, remaining, forecast, kits, reservations, tile summaries and menu badges are computed server-side; paging, sorting (computed keys through `list_paging.sort_computed`, the forecast keys `ready`/`hours` through ONE `farm_forecast.forecast_projects` walk per request — no cache, by the owner's call), search (Unicode-folded) and filters are request parameters, and the place in a list lives in the URL. The frontend never sorts or filters a loaded page into another list and never adds rows up into a number the server could return. Tiles are a FARM summary (`GET /projects/summary`, `/customers/summary`, `/stock/figures`), deliberately NOT following the list's filters — they sit above them. A customer's `total_price` (and on the detail `ordered`/`printed`/`covered_units`) leaves cancelled orders out; `total_cost` counts every order. «Overdue» is one rule — due before the start of today — in `utils/orderDates.isOverdue` and in the orders summary. Vault: `40-invariants/inv-workshop-lists-and-figures-on-the-server.md`.

## A Workshop entity's code is derived from its id, in one place (WS-03, 2026-09-26)

`services/entity_codes.py` holds the prefix table — `CU` customer · `CT` contact · `OR` order · `PR` product · `SK` stock item · `DN` dispatch note — and the two functions every caller uses: `code_for` (``OR-0042``: the id zero-padded to four digits, growing past four) and `id_from_query` (any case, any number of zeros, prefix optional unless `require_prefix`; a foreign prefix names nothing; an id past 2³¹−1 is text, never a bind overflow). Codes are Latin and never translated; responses carry `code` and the frontend never builds one. A new entity of the section gets its prefix THERE, and a test pins that prefixes are two letters and unique. ⚠️ A code is never reissued only while the id is not: SQLite without `AUTOINCREMENT` hands out `max(id)+1`, so deleting the newest row gives its id — and its code — to the next one. A new table whose id becomes a code is created with `AUTOINCREMENT` on SQLite (in its migration, and `sqlite_autoincrement` in the model for `create_all`), as `customer_contacts` and `delivery_methods` are; `customers` / `projects` / `products` predate the rule. Vault: `40-invariants/inv-workshop-codes-derived-from-id.md`.

## An order's journal has one writer; its stage is a manual column (WS-04, 2026-09-26)

`project_events` (m191) records every operator action on an order — only `services/order_journal.py::record` writes it (`tests/unit/test_order_journal_has_one_writer.py` scans the tree), in the caller's transaction, never committing. `kind` is the closed `EVENT_KINDS` list, mirrored by `frontend/src/components/projects/orderJournal.ts` and pinned against both locales in `locales.test.ts`; `payload` holds codes, ids, numbers and name snapshots — never a sentence, the feed composes it in the reader's language. The actor is `user_id` + a `user_name` snapshot; `created_at` is stamped by the writer in Python UTC — the clock print events use — never left to a server default, which is local time on a PostgreSQL whose timezone is not UTC. `/projects/{id}/timeline` merges the journal with prints and queue rows; the synthetic `project_created` appears only for orders from before the journal. SQLite runs no FK actions: deleting an order deletes its journal (`delete_for_project`), deleting a user nulls `project_events.user_id` (`detach_user`) and `projects.responsible_id` in code. **`projects.stage` (`prep`/`printing`/`qc`) is set by hand only**, through `PUT /projects/{id}/stage` — the owner rejected every derived stage (per-request, sweep, event-driven: 2026-09-26); «done» is `status=completed` and never stored; filters, sort and `totals.stages` are plain SQL over the column. Vault: `40-invariants/inv-order-journal-single-writer.md`.

## A product's stored facets have one writer, and it follows the plate writer (WS-07, 2026-09-27)

`product_facets` (m191) — a product's plate materials, colours and printer models, one row per `(product_id, library_file_id, kind, value)` — is written only by `services/product_facets.py` (`refresh` / `refresh_all` / `delete_for_product` / `delete_for_files`; `tests/unit/test_product_facets_have_one_writer.py` scans the tree). The catalog filters and searches them in SQL, so they are STORED rather than parsed out of every linked file's metadata per request (owner's call). Plates have one writer (`product_sync`) and every rewrite of a file's metadata (re-scan, MakerWorld re-download, the objects backfill) ends in that sync, so the facets are refreshed exactly where the sync changes plates: `sync_product_for_file` at EVERY return (the geometry-file early return too) for linked-before ∪ desired ∪ owners of existing plates, and `purge_file_product_links` for the plate owners read before the delete; every other door (folder, inheritance, resync, duplicate, from-file) ends in `sync_product_for_file`. A row names its FILE, and every reader goes through `product_facets.visible_facet` (or joins `library_files.deleted_at IS NULL`): a trashed file's rows are skipped at read time, as the product's plate list skips them (owner, 2026-09-27) — so the trash and restore doors, which do not pass through the sync, need no hook. Values are normalised as `product_composition` reads them (type and colour upper-cased, model through `normalize_model_name` — the model filter normalises its input the same way). The writer uses Core delete + insert, never ORM objects — a same-session reader's identity map would collide on the primary key — and sends ids in `SQL_CHUNK` batches (`id_chunks`). SQLite runs no FK actions: `product_delete.delete_product` removes the rows in code. Beside it, the product's catalog fields: `sku` (+ `sku_key`, casefolded, sized for casefold's threefold growth, unique when set; a clash is 409 before the write and again when the unique index settles a race), `version`, `category_id` from the `product_categories` directory (delete leaves products uncategorized, in code) and `status` `draft`/`ready` — `ready` is refused (409) without a part and a plate outside the trash, checked before any write, and never demoted by the server. The frontend refreshes the catalog's figures through `utils/queryInvalidation.invalidateProductCatalog`, never `['products']` alone. Vault: `40-invariants/inv-product-facets-single-writer.md`.

## An order line's kit has one reader, and its configuration one writer (WS-08, 2026-09-27)

A product may carry variant groups (`product_variant_groups` / `product_variant_options`, m191); a part's binding is a SET of options across groups — `product_part_options (part_id, option_id, group_id)` (m225, which replaced `product_parts.variant_option_id`), read through `ProductPart.bound` (`group_id → option ids`) — and `line_composition.in_kit` is the one rule: the part is in a line's kit when, in EVERY group it has options in, the line chose ONE of them («and» across groups, «or» within one); a part with no rows is in every kit. Bindings have one writer, `product_variants.set_part_options` (`tests/unit/test_part_options_have_one_writer.py`); a part's rows go with the part through the ORM cascade (`ProductPart.option_links` — SQLite runs no FK actions), and an option or a group cannot be deleted while a part is bound to it (409). `ProductPart.qty_per_unit` is the product's STANDARD count, so what a line is made of is asked of `services/line_composition.py` alone (`composition`, `line_composition`, `compositions_for_lines`, `per_by_line`, `standard_composition` for the catalog's kits, `standard_per`) — `tests/unit/test_line_composition_is_the_one_reader.py` fails on a `.qty_per_unit` read outside its allowlist (product authoring, the stock ledger's "has a shelf" predicate). Figures, reservations, the stock tab, order filing and the line response all read per-line compositions. `project_line_choices` (a choice for EVERY group, the standard too — a later standard or a new group never changes a saved order), `project_line_part_counts` (only counts that differ from what the choices give; a `parts` line's wanted counts) and `project_lines.config_key` are written by `services/line_config.py` alone (`tests/unit/test_line_config_has_one_writer.py`): `seed_line` at every line constructor (create order, add line, order from files), `copy_configuration` on an order copy, `add_group_to_lines` when a group is added, `forget_part` / `repoint_part` / `forget_line` in code (SQLite runs no FK actions), `set_configuration` behind `PUT /projects/{id}/lines/{line_id}/configuration` — which moves the line's reservation to the new kit in the same transaction and journals `line_configured` (a no-op writes and journals nothing; a COMPLETED order is 409 — its kits shipped, moving the reservation would put them back); `dry_run` writes nothing and answers how much of the printed and queued parts would BECOME surplus. Changing a part's binding freezes every saved product line and stock position whose kit it would change (`freeze_binding` takes the NEW binding, compares the kit under both and writes the old count), so a saved order never moves under a product edit of this kind. A part the line's configuration dropped but the order printed stays on the line as a `per = 0` figures row (surplus, bankable); "has a shelf" is ONE predicate, `line_composition.has_shelf` (`part_stock.is_counted` delegates) — printed and not marked «не рахувати» (`product_parts.ignored`, m191): a zero in the kit is a part OUT of the kit, with a shelf, and the mark (only on a zero; 422 otherwise, 409 while the part holds stock or a line or position wants it; every pre-existing zero got it once in m191) is what says «not a part» — no shelf, no need, and `line_config` refuses a count for it (422); only a shelf part's surplus is bankable. A `parts` line has quantity 1 for good and takes nothing from the shelf (422). Deleting a standard option, one a line chose or one parts are bound to is 409. `product_variant_groups.default_option_id` deliberately has no FK (it would close a group ↔ option cycle). Variant groups and options have ONE writer, `services/product_variants.py` (`tests/unit/test_product_variants_have_one_writer.py`); the single routes are thin doors to it, and `PUT /products/{id}/variants` applies a whole draft in one transaction against `variants_revision` (SHA-256 of the canonical groups, by id) — a stale draft is 409 `variants_changed`, a refusal half way writes nothing, a draft without changes writes nothing (WS-13 E1 VR). **A new line takes only an available combination (spec product-part-variant-combinations).** One pure function decides it, `line_composition.availability(parts, choices, sliced, strict_groups)`, on the choice's STANDARD kit (changed counts never open a closed one): in every group marked «every value needs its own part» (`product_variant_groups.requires_part`, default off, written only through `product_variants` and part of `variants_revision`; `combination_gate.strict_groups`) that some counted part — a standard count, not «не рахувати» — has options in, the chosen option must be named by a part of the kit (`option_without_part`; an unmarked group, or one no counted part discriminates on, closes nothing — an optional add-on keeps its «no»; when a chosen value is named by no counted part at all, only such values are reported), and for every product with groups each printed part of the kit needs a sliced source (`part_not_sliced`). Marking or unmarking a group moves no saved line or position (no freeze, no re-key). `services/combination_gate.py` reads the sliced set and refuses through `ensure_available`, asked in `line_config.seed_line` for a `product` line (so every constructor: create, add, batch, order from files — a call adding several lines passes one `sliced_memo`, so each product's sliced set is read once per call) and in `set_configuration` only when the CHOICES change, decided against the saved choices merged over the product's standards (the choices the kit reads): a counts-only change is never gated, even on a line saved without a row for a group, and a dry run of a CHANGED closed choice is refused too. Never on an order copy, a `parts` line or a stock door (receipt, stocktake and assembly take any configuration), and a product without groups returns before any query; a saved line whose combination closed later keeps it. The refusal is 409 `{"error": "combination_unavailable", "message", "reasons": [{code, group, option, part}]}` — name snapshots the frontend composes (`partBinding.reasonText`), carried through `line_intake` for a batch; the frontend reacts to the code, never the text. Two read routes answer the same rule with the same reasons and write nothing: `GET /products/{id}/combinations` (the paged table) and `POST /products/{id}/combination` (one choice and every value's `available_here` / `available_anywhere` — `null` past `MAX_ENUMERATED`), both `products:read` — facts of the product's structure (owner, 2026-11-14), so an order manager without stock rights sees the marks; the dialogs ask under `utils/workshopRights.canReadProducts`. The order dialogs only carry that answer (`components/projects/useCombinationState.ts`, whose `optionState` / `optionLabel` are both dialogs' one rule for a value): a value that would close the choice is marked in words and stays clickable, one in no available combination is off unless chosen or the line's own, and Add / Save wait for the answer, refuse a closed choice and are described by the note that says why — the line's dialog only when its choices differ from the saved ones. Vault: `40-invariants/inv-line-composition-one-reader.md`, `40-invariants/inv-line-configuration-one-writer.md`, `40-invariants/inv-part-binding-and-combination-availability.md`.

## Every door that moves a product's configuration, orders or stock goes through the product gate, and locks in one order (WS-13 E1, 2026-09-29)

Waiting locks are taken in class order, ascending id within a class: `library_files` → `products` (the GATE) → `projects` → `stock_items` → `project_lines` → `product_parts` → `project_procurement`; a door that needs several takes them in that order and never goes back to a lower class. The gate is `services/product_gate.py::product_gate(db, product_ids)`: `FOR NO KEY UPDATE` on PostgreSQL (`take_write_lock` on SQLite), taken FIRST in a clean session, ascending — on its first entry it refuses (`GateOrderError`, in production too, never logged-and-continued) a dirty session, a lower id than one it holds, or a caller already holding a lock of class ≥ 3; re-entry does nothing and issues no SQL; a product this transaction created is skipped. Multi-line doors take positions → lines → parts through `finished_stock.lock_lines_with_parts`; a line door locks the positions first (`lock_line(also_keys=…)` names the configuration it is about to move to) and a set of positions that changed under it is 409 `stock_changed`, never a late lock. Variant and configuration writers never WAIT behind the gate: their footprint is taken `FOR UPDATE NOWAIT` (`lock_nowait`), and SQLSTATE 55P03 — read off `core/database.sqlstate`, never the driver's exception type — answers 409 `{"error": "product_busy"}`. `core/lock_ledger.py` records what the OUTER transaction holds across savepoints (a snapshot at a savepoint's start, kept on RELEASE, restored on ROLLBACK TO; rows the transaction INSERTed are marked by an `after_flush` listener and never lock-contended); its monitor raises on an out-of-order lock under `BAMDUDE_LOCK_ORDER_STRICT=1` (the test conftest sets it) and logs once per key in production. The PostgreSQL scenarios (`tests/integration/lock_protocol_scenarios.py` + `test_postgres_scenarios.py::TestLockProtocol`) stop session A inside its operation on a named barrier and watch session B in `pg_stat_activity` — a test that runs A to completion before B starts cannot see a deadlock. Vault: `40-invariants/inv-product-gate.md`.

## Finished goods are columns and a ledger with one writer (WS-09, 2026-09-27)

`stock_items` (m191) holds one position per product configuration — `UNIQUE(product_id, config_key)`, the same key as an order line, `AUTOINCREMENT` for its `SK-` code — with `on_hand` / `reserved` / `min_qty` / `location` as COLUMNS: lists, filters, sort, tiles and the sidebar's «below minimum» (`min_qty > 0 AND on_hand − reserved < min_qty`) are SQL over them, and CHECKs keep `0 ≤ reserved ≤ on_hand`. `stock_item_movements` is the history, with its actor. Only `services/finished_stock.py` writes either (`tests/unit/test_finished_stock_has_one_writer.py`): it locks the position row for each read-decide-write — `FOR UPDATE` on PostgreSQL; on SQLite, whose dialect emits none and whose pysqlite opens a transaction only at the first write, `core/database.take_write_lock` takes the write lock with a no-op UPDATE BEFORE the read (two reservations both landed without it; `part_stock.lock_part` does the same for the parts ledger) — and moves the columns and the ledger together — the columns always equal the sum of the movements — and never writes a zero row; the kinds are the closed `MOVEMENT_KINDS` (frontend copy `STOCK_ITEM_KINDS`, labels in both locales). A stocktake takes the COUNTED quantity and records the difference (below the reservation is 409; a lower count needs a note). A position's configuration (`stock_item_choices` / `stock_item_part_counts` / `config_key`) is `line_config`'s, like an order line's: `resolve` applies the same rules, and every product edit that moves line configurations (`add_group_to_lines`, `freeze_binding`, `forget_part`, `repoint_part`) re-keys positions too — 409 when two positions would become one configuration. Assembly is one transaction over both ledgers: the kit's printed parts (through `line_composition`) leave the free shelf by `part_stock.move(reason="assembled", stock_item_id=…)` and the position grows; bought parts are not written off. Both ledgers stamp `created_at` in Python UTC (a server default is local time on a non-UTC PostgreSQL), and `GET /stock/journal` merges them on a `(created_at, book, id)` keyset at full microsecond precision — never truncated (SQLite's `strftime('%f')` rounds where Python truncates, and a page boundary lost rows); legacy parts rows on SQLite (no fraction) are padded to six digits before they are compared. With `page` set the journal answers numbered pages instead (WS-13 E1 ST1): one `UNION ALL` of both books' `(ts, rank, id)` keys built from the SAME filtered queries and timestamp expressions as the cursor (`stock_journal._finished_query` / `_parts_query`), ordered and cut in SQL, then hydrated by id — the two modes give the same rows in the same order; `page` with `cursor` is 422. A position is created by a receipt, a count above zero or an assembly, serialised on the product row; a deleted customer is detached from issues in code (`detach_customer`); an API key's writes are recorded against its owner (`core/auth.acting_user`). SQLite runs no FK actions: deleting a product is 409 while anything is on hand or reserved and removes its empty positions in code (`delete_for_product`); deleting a user nulls the actor in both ledgers (`detach_user`). Vault: `40-invariants/inv-finished-stock-single-writer.md`.

## What an order line takes from stock is decided by ONE function, and lines are added in ONE transaction (WS-10, 2026-09-27)

`services/stock_pick.py::suggest` is the only place that answers "how much of this line comes off the shelves": ready units of THAT configuration's position first (`min(quantity, free)`), then kits of free parts on the rest, the remainder to print; it writes nothing, runs a fixed number of queries for any list (named lines included — they are read together), and with `line_id` counts what the line already holds, and what it already issued on a reactivated order, as its own. `POST /stock/suggest` (the «Add to order» dialog, «Pick from stock» on a line) and the batch's `stock: "auto"` both call it — the frontend never computes a proposal, it only clamps the operator's own numbers to the «of N» of the same answer. `POST /projects/{id}/lines/batch` (`services/line_intake.py::add_lines`) takes `product` / `parts` / `plate` lines in one transaction — a refused line adds nothing, with that line's own sentence and no line number; `POST /projects/{id}/lines` and order creation run the same code with one line. A library file an order names (a `plate` line, every kind of `/projects/from-files`) passes the library's own ownership gate (`routes/projects.py::_library_visible` over `library._library_file_visible`): a caller who sees only its own files uses only those, another user's file is the same 404 as a missing one. What the shelf gives may be less than asked (it moved since the proposal): the writers reserve `min(asked, free)` under their locks and the answer carries `asked_*` / `got_*` — clamped, never refused; an `auto` row is re-picked at confirmation, so its `asked` equals its `got`, and the dialog compares `got` with what the row SHOWED. The ready units a line took live in `project_lines.from_finished` (m191), written only by `finished_stock` (its guard test covers the column); only an ACTIVE order takes them (PATCH on another is 409), completion goes through issuing (WS-11, below) and the column keeps what was issued («issued included», so a completed order's coverage does not drop), cancel / line or order delete releases, a configuration change moves them to the new position as far as it has free, a lower quantity gives kits back first. `reserve_for_line(units)` takes the line's TOTAL, issued included — a reactivated order's line never takes more for asking for fewer, and never gives back what shipped. Every line door locks the line row before it reads what the line holds (two releases of one line hand back once), and closing or deleting an order locks all the positions its lines hold in ascending id order first (two orders never lock them in opposite orders). ⚠️ `from_stock_units` means two things: in REQUESTS (`ProjectLineCreate` / `ProjectLineUpdate`) it is still KITS (API compatibility); in the FIGURES it is every unit from stock, split as `from_finished` + `from_kit_units`. Line movements on the finished-goods ledger carry no note — the order's journal says why (a write-off carries the operator's own). The frontend invalidates with `invalidateOrderViews` alone: `ORDER_VIEW_KEYS` holds every stock key a line moves (`product-kits` joined it), and a second `invalidateStock` refetched the product page twice. Vault: `40-invariants/inv-stock-pick-one-function.md`.

## An order's goods are issued through ONE function, and an order completes only fully issued (WS-11, 2026-09-27)

`services/order_fulfilment.py` answers what each line can assemble, receive and issue now (`state`, with the order's `can_assemble` / `can_receive` / `can_issue` totals the banner shows — never summed on the client) and performs a batch (`apply`): the positions its lines hold locked in ascending id, then the lines, then the state read AGAIN; a number above it is a 409 sentence and nothing is written (an issue is physical units — refused, never clamped); per line assemble → receive → write off → issue; at most ONE `stock_issues` row per batch. Receiving obeys BOTH the line's eligible printed output (including material) and the shared order print budget: a per-line bound alone can credit the same print twice, while the shared budget alone lets one material receive another's print. The line's own partial stock reservation can complete a mixed kit without being credited as new printed output. Already received printed extras also consume that shared budget; their receipts keep the same line eligibility. A line of a product without printed parts is received as its units come. The positions a batch writes — held ones AND each line's own configuration — are locked in ascending id before the lines (`lock_positions_for_lines`), assembly locks the position before the parts, and the status is read again under the locks. The line counters `project_lines.assembled` / `received` / `issued` / `returned` / `written_off` (m191) are written only by `finished_stock` (its guard covers them), a parts line's by `part_stock` in `project_line_part_stock` (own guard); held on the shelf for the order = `from_finished + assembled + received − issued − returned − written_off` = Σ `delta_reserved` of the line's finished movements. What belongs to an order never reaches the free parts balance: `reservation_released`/`assembled`, `made_for_order`/`held_for_order`, `hold_released`/`issued_for_order`, `hold_released`/`written_off_for_order` are zero-sum pairs, and a cancel lifts the hold alone. A write-off (movement `written_off`, a note required — 422 without) is a unit that broke on the shelf: the order needs it made again — its need and its surplus count `quantity + written_off` (a parts line: `per + written_off`), so the plan prints one more and the replacement is not surplus. `stock_issues` has one writer (`services/stock_issues.py`, guard test): a recipient SNAPSHOT (name, phone, delivery method NAME, details), a waybill ≤ 24 characters and a note — the only two things `PATCH /stock-issues/{id}` changes; both ledgers' movements carry `stock_issue_id`; a manual issue off the stock page names its customer (422 without). An issue IS its dispatch note (`DN-<id>`, WS-12): `stock_issues.seal` writes the snapshot — `stock_issue_lines`, supplier details, basis, performer, units — once, in the issuing transaction after the movements (409 twice or empty); the list and the document (`GET /stock-issues/`, `/stock-issues/{id}`) are drawn only from it, so a product delete (whose movements go) or a rename changes no note; the writer owns both tables (same guard test), and `detach_product` nulls a deleted product's link in code. The note's white sheet (`DispatchNoteSheet.tsx`) is the one sanctioned exception to the app's colours, and it prints alone through one `index.css` rule scoped to pages carrying `[data-print-sheet]`. `PATCH status=completed` asks the same `state` (`can_complete`) — 409 unless everything is issued; an order WITHOUT a customer (judged by the customer the request ends with) issues nothing and closes to stock once everything is on the shelf or issued (`closes_to_stock`, `order_fulfilment.close`: the cancel's doors — held units and parts become free, `returned` grows — with the status «completed», journal `goods_stocked`), and such an order is not reactivated (409, like a cancelled one whose stock moved); completion releases the kits nobody assembled (note `order_completed`); every «done» door in the frontend opens the dialog. After a line's first movement its ready-units number and its configuration are 409 and its kits only come DOWN (back onto the shelf; more is 409) — only «take from stock» adds (`services/stock_offers.py`: the plan's unplanned units through `stock_pick.suggest` WITHOUT `line_id`, clamped to what was shown and to the shelf) — and its quantity stays ≥ issued + held; cancel / delete gives back everything held (`give_back_for_line`, `return_parts_for_line`, unassembled kits), issued stays issued, and a cancelled order whose stock moved is not reactivated (409 — duplicate it). A print whose output the order received cannot leave it (409 at both un-file doors — `order_fulfilment.ensure_prints_can_leave`), and deleting an order whose stock moved credits no parts to the free shelf: those parts are finished units on the shelf or with the customer. Received units stay covered in the figures even when defects are recorded on their prints later — receiving is the check. SQLite runs no FK actions: an order delete detaches its issues, a line or part delete removes the parts-line counters, a part merge moves them; a one-off product that ever had a stock position outlives its deleted order — its movements are the issues' units and the journal. Vault: `40-invariants/inv-order-fulfilment-one-function.md`, `40-invariants/inv-stock-issues-single-writer.md`.

## Free stock of product parts is a LEDGER with one writer (m162)

`product_part_stock_movements` holds signed movements per product part (`surplus_banked` · `unfiled_print` · `reserved_for_order` · `reservation_released` · `manual`); the balance is Σ delta, never a column. **Only `services/part_stock.py` writes the table** — routes, `on_print_complete`'s `_credit_free_stock` hook and the part/product delete–merge paths call it; readers may live anywhere. The writer never writes a zero row, enforces the sign per reason, locks the part row for its read-decide-write (`lock_part_stmt`, `populate_existing`) and refuses a balance below zero (`PartStockError` → 409). Two rules the user chose: an order's surplus goes to stock only by the **button** (`POST /projects/{id}/bank-surplus`, differences only); an order-less completed print goes to stock **automatically** (idempotent by the archive's NET); filing it under an order later reverses the credit, un-filing re-credits (symmetric). A line reserves whole kits, clamped to `min(asked, quantity, kits_available)`; every "still needed" figure subtracts the reservation and the order-level sum caps it per line. ⚠️ SQLite ignores FK actions — CASCADE/SET NULL are done in code through the writer (`delete_for_part(s)`, `repoint`, `detach_archive`, `detach_line`). ⚠️ Backend-written notes are tokens from `NOTE_TOKENS` (the frontend translates them); free text is the operator's own only — a `manual` adjustment, or the note of an order's write-off. Vault: `20-systems/products.md` §Залишок, `40-invariants/inv-stock-ledger-single-writer.md`.

## Defects have one writer, and the shelf follows them (2026-09-11)

`services/archive_defects.py::record_defects` is the only thing that sets `PrintArchive.defective_count` / `print_archive_parts.defective` (the pre-existing Skip Objects hook and the m158 row-seeding rule stay): a per-part value is absolute and clamped to the row, `defective_count` is the SUM of the rows when rows exist — a flat count sent alongside rows is ignored — else the clamped flat value. Four doors call it: `PATCH /archives/{id}`; the order page (`POST /projects/{id}/archives/{archive_id}/defects`, `ORDERS_UPDATE`); both plate answers (`clear-plate` / `repeat-print` with an optional `defects` body under `PRINTERS_CLEAR_PLATE` — the waiting archive is resolved BEFORE the answer releases the hold row, and the helper never commits, so a refused repeat rolls the defects back); and the Telegram prompt (`telegram_handlers/defects.py`, registered ABOVE `actions_router` because that router ends in a catch-all `action:` filter; the completion message's «Брак…» button carries the archive id threaded through `archive_data` → `extra_data` and is omitted when the completion could not be attached to an archive — never a "newest completed" guess, which pointed at the previous print). After the write the writer calls `part_stock.adjust_unfiled_print`: for an order-less completed print with a library file it writes `wanted − standing` per product part as `manual` + `archive_id` + `NOTE_DEFECTS_RECORDED`, only where `standing > 0`; an unresolvable `wanted` (`{}`) does nothing; a refusal below zero is RETURNED, never raised — the defects stay recorded (the archive is the print history) and the refusal is reported where it can happen (card toast, Telegram line; the order route never sees one — a filed print was never credited). ⚠️ `seed_archive_parts` applies a standing flat count to freshly seeded rows (`apply_flat_defective`, mono-plate rule): an external print completes before its 3MF arrives, so the flat count typed at plate-clear must survive the rows that come later. ## A working order plan is consumed only by committed publication receipts

Autosave changes the shared draft; only explicit Save changes its comparison baseline. The existing source/lane guards precede Project/ProjectLine FK key-share guards, then draft → operation → receipt. Queue rows, receipt, draft decrement and the operation's first comparison-epoch advance commit together. Capture and network I/O never hold the draft guard. Replays read receipts, cancellation fences only unpublished work, and queue cleanup never returns counts automatically. A lost response must reconcile both the payload and revision from the server before editing resumes; loading a new revision and writing old pre-submission counts would duplicate work. The editor takes quantities, revision and epoch from one working-plan response; project-plan supplies metadata only, and no acknowledged local overlay survives another revision. A reviewed replan applies its signed entries instead of recomputing against live fleet capacity. Admin cancellation fences only an explicitly addressed unpublished remainder with current scope and an audit, never transfers authorship. Lifecycle fences follow stock/line locks. Nominal machine-hours sum selected slicer time independently of farm occupancy; incomplete working coverage never promises whole-order readiness. ## A part's picture has one writer, one reader, and its name → part mapping is decided at read time (part thumbnails E4)

`services/part_images.py` alone writes `product_parts.image_*` and the photos under `products/<id>/part-images/` (`tests/unit/test_part_images_have_one_writer.py`), and alone answers which picture a part shows (`resolve`), the editor's state and the candidates. Nothing caches a resolution: instances come from the file metadata on every read (`product_composition.plate_objects` → `part_names.tally_objects` → `part_index`), so a merge, a split or a new alias changes the picture without a write; a pin that no longer holds falls back to auto and says why (`file_unlinked` / `file_trashed` / `object_gone` / `not_this_part` / `not_rendered`), never re-pins itself. Every route whose answer carries a shape of `part_image_shapes()` is decorated `@part_images.attach` and fills the pictures in one read per kind — the parts', and the plate objects' when there are any — best effort, in a savepoint: a lookup that fails leaves the pictures out, never the route's write (`tests/unit/test_part_image_shapes.py` walks every schema and every route). The WebSocket event `part_images_changed {product_ids}` goes after the ROOT commit only — `mark_changed` collects on the session, a rolled-back savepoint takes its own marks and files with it; the render writer reports through `mark_renders_changed` in its own transaction, and only a transition that moves a plate's status or result, never from a background session (in the tests every session shares one connection, and closing any of them rolls back everyone's work). The event says `images_only` only when EVERY mark of its transaction came from a picture-only door — `set_choice`, `set_photo`, `clear_photo` and the render transitions (`tests/unit/test_part_images_pure_doors.py` lists them); the session keeps the products a structural mark named beside all the marked ones, savepoints included. A picture-only event refreshes the pictures and the product views only (`PART_IMAGE_PURE_KEYS`) — never a stock or order figure, so an open G08 dialog keeps its numbers and its primary (spec procurement-stock-images). Every file operation of the writer runs through `preview_artifacts.disk`, which a cancelled caller still waits for, and is all-or-nothing: a photo or a copy that does not get its name leaves no file, even when the caller catches the error and commits. A photo is never stored as sent: its orientation goes into the pixels and it is saved again in its own format with only its colour profile, so EXIF (GPS, the camera's serial), XMP and comments never reach the readers of orders and stock or an export — and what was saved must fit `attachment_limit()`, the cap the import asks of it (413 otherwise). An imported pin is kept only when it holds on the new farm (in the columns' range, a linked plate, an object of this part) — its pixels come later. The frontend shows every part picture through `components/PartThumb.tsx` (`PartThumb` for a part, `InstanceThumb` for a plate object — never a hand-built `<img>`); a stock or order view uses `LivePartThumb`, which reads its part's picture apart from the view's answer — `GET /product-parts/images` (product + picture off one row, not `@attach`: a failure is the request's, never «no picture»), one request per tick through `utils/partImageBatch.ts` (a transport, not a cache), cached under `['part-image-refs', id]` with no `initialData`; `partThumbLiveReaders.test.ts` fails on a plain `PartThumb` outside its listed exceptions. A structural event drops the cached pictures of the products it NAMES (`refreshPartImageRefs`, spent at the socket's debounce flush, never per event) — SQLite gives a deleted part's id to the next part — and leaves every other product's picture on screen; a picture with transparency (a render) sits on the mat its part's tone asks for (`components/partTone.ts`: read off the loaded picture through a canvas at its own size, 128 px a side at most — the mean of its opaque pixels, or, for a part too thin to have any, of every visible pixel weighted by its alpha; a dark part on the light mat, a light part on the dark one, the same pair in every theme), because no one backdrop reads every filament colour (measured 2026-10-11); a photo, a glyph or a broken picture keeps the theme's frame; its larger picture owns its Escape in the capture phase on `document`, so one Escape closes it alone and a newer modal's Escape is left to that modal. The part editor saves in two steps — the part, then its picture — adopting each answer as its editing base, so a refused picture keeps the dialog open on the saved part and a retry sends the picture alone; the saved picture it shows is a live read model (`product.parts` by the base's id, refreshed by the event and every write), apart from that base, and a picture draft the operator has not touched follows the saved choice. Vault: `40-invariants/inv-part-image-resolved-at-read.md`.
