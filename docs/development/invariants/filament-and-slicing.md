# Invariants: Filament, AMS, spools and slicing

Full text of the rules that [`CLAUDE.md`](../../../CLAUDE.md) keeps in short form, with the reasons and the history behind them. `Vault:` pointers name notes in the maintainer's private knowledge base; everything a contributor needs is here.

## A tray number is computed in one place (N01 stage A, 2026-11-28)

A global tray id — what `tray_now` reports, what `ams_mapping` holds, what usage, unlinking and every slot label go by — is computed, split, compared and labelled only in `backend/app/utils/tray_ids.py` and its twin `frontend/src/utils/trayIds.ts` (no mask helpers there: the backend decodes the bit masks, which reach bit 45). The table is Bambu Studio's (`DevAmsType`, `GetTrayIndexMap`): a regular AMS `ams_id * 4 + slot`, an AMS-HT its own id, the A2L's AMS Lite `24 + slot` (stored as unit 6; the 16 → 6 fold belongs to the helper), an AMS 3H `28 + slot`, an AMS 3P `37 + slot`, an external input its own id. A unit's type is bits 0-3 of its `info`, stamped on the unit and kept across deltas without `info`; a unit never seen with a type is told by its id (6, 32, 33, 128+) — a deviation from Studio, which takes such a unit for an AMS and would fold the AMS 3H into the AMS-HT range. Slots are stored `(ams_id, tray_id)`; every external input under 255: 254 → 0, 255 → 1, 247 … 253 → 2 … 8. That index is not monotonic in the PrintTool, so order, labels (`Ext-n`) and bounds go through the PrintTool `256 − v`. Numbers 28-45 are a rack AMS's unless the printer lists a regular unit 7+ (none exists).

A direct-connected rack (H3C, P3C) is one toolhead — never "two nozzles". Studio knows it from `print.device.holder.info2` (bits 1-4, above `RackType_AB`); the H3C's own frames carry no holder, so the mirrored config's `default_nozzle_count > 2` — the test Studio uses for `Ext-n` — says it until one is seen. The rack size is the number of external inputs (`GetTotalRackNozzleCount`), until those are seen the same config value. Its tray now is `device.extruder.info[0].snow`; a frame without it carries the rack's bare slot, read only when `0 <= k < N` (upstream's hardware observation). Its toolhead temperature is `extruder.info[0].temp` and `nozzle_temper` is not read (after a swap it reports the hotend put back). `TrayLayout` is the one per-printer answer; `PrinterManager.tray_layout`, or `tray_layout_of` where a stand-in manager may be handed in — anything not a `TrayLayout` is no layout.

Printing on a direct rack (N01 stage B) follows Bambu Studio. The tray decides the PrintTool — rack slot k feeds PrintTool k + 1, input v feeds `256 − v`, a sub-AMS tray the hotend whose `bind_ams` lists its unit — and no `nozzle_mapping` is sent (`nozzles_info`, V0, V1 never apply there). `utils/direct_rack.py` reads the hotends (`device.nozzle.info` by `addr_id`, the `exist` mask by full id, `hc`, the inlet flag of `stat`, each entry's own `snow`, `bind_ams`, the dock bits of `holder.info2`) and owns Studio's rules: the one bound slot of a hotend (`sTraverseBindAmsSlot`: its `snow`, else its rack slot unless TPU285 on a type-A rack, else its input), `QuerySlotFeedBlock` (manual feed, blocked by an external or rack-AMS occupant) and the diameter / flow match. The feed snapshot carries each source's hotend (`rack_addr`) and block, the rack in its revision; routing (`filament_routing._rack_source_fits`, `rack_preconditions`) takes only bound trays whose hotend fits, an automatic plan no blocked one (a pin may, with a notice), and lets two filaments share a tray. The wire is `direct_rack.project_file_entry` (rack slot `{32|33, k}`, inputs 247-253 raw, 254 / 255 as `-1`, raw for a calibration print), `use_ams` false only when every tray is 254 / 255. The slot setting and its reset go out in Studio's form (`filament_setting_ids`). `tray_now` 255 is PrintTool 1's input only when the toolhead's `snow` said so (`PrinterState.direct_rack_input_loaded` → `TrayLayout.main_input_loaded`; `tray_ids.names_loaded_source` for the readers); a bare 255 changes nothing.

Until N01 stage C, `services/direct_rack_gate.py` refuses, by name, loading and unloading, an RFID re-read, drying, the K-profile of a slot (`extrusion_cali_sel` / `extrusion_cali_set`, keyed by `nozzle_pos` in Studio) and the automatic calibration on a rack AMS slot or a rack's input. A manual calibration prints: its row is exempt from routing, so `start_calibration` and the exempt branch of `preflight_item` ask the hotend its tray leads to (`filament_routing.calibration_hotend_refusal`), and the session ends `printed` with no save step (`save_result` refuses). A regular AMS bound to a rack printer is not refused, and every other control (stop, pause, light, fans, temperatures, G-code) is unchanged.

Why: before this ~40 hand copies each got the new printers wrong in their own way — unit 32 landed on the AMS-HT range, inputs 247-253 read as AMS-HT, the H3C's `tray_now` as a local slot — and a spool was charged, unlinked and labelled on the wrong slot, silently. The guard (`backend/tests/unit/test_tray_numbers_have_one_home.py`, its twin `frontend/src/__tests__/utils/trayNumbersHaveOneHome.test.ts`) fails any hand-written numbering form outside the helper; what stages B/C/D still own is named with its stage, and an exemption that no longer matches fails too. One table answers both twins (`frontend/src/__tests__/fixtures/trayIdCases.json`); `test_tray_ids_parity.py` keeps the replaced formulas as the reference for every other printer. Vault: `40-invariants/inv-tray-number-one-home.md`.

## Filament attribution believes the DISPATCHED mapping, never the live one

AMS filament backup swaps trays mid-print and rewrites the MQTT `mapping` field to the substitute, so read at completion it charges the whole print to the spool that only finished it. Priority in `usage_tracker._track_from_3mf`: stored print-cmd `ams_mapping` → queue item's `ams_mapping` → live `mapping` → colour match → `tray_now`. Both dispatched sources outrank the live one; don't reorder. Everything the split needs survives a restart in `active_print_sessions` (one row per printer, internal counterpart of `active_print_spoolman`, and the only carrier of `tray_change_log`) — written at start, appended by the `on_tray_change` callback chain, restored in `on_print_running_observed` **only** when it belongs to the running print, dropped at completion. Belonging is the row's `archive_identity` (m221: the `recovery_identity` its start bound, stamped by `usage_tracker.claim_session` after the bind or at an adoption's creation), never a name: an A1 mini reports `X.3mf` for `X` after a power cycle, and two prints can share a folded, truncated, legacy or exact name (GH #115). `owner_tracked` marks every row an owner-aware start wrote, so an unclaimed start stays unclaimed across a restore, Spoolman mode included. `usage_tracker.session_belongs_to` is the one rule: a stamped session belongs to that archive alone, and no completion path lends one stamped with another archive; an unclaimed start is never lent; only a pre-m221 row keeps the exact-name rule. The restart restore proves a stamped row through `_live_archive_for_running_print` and acts only on the row snapshot it decided on (`read_persisted_snapshot`, `restore_session(expect=)`, `clear_persisted_snapshot`), deciding again when a newer start replaced it; it deletes only a pre-m221 row of another print, leaving a stamped or unclaimed one to its owner. The reconcile deletes only its own archive's row (`clear_persisted_session_of`). Capture runs for BOTH inventory backends; `spoolman_owns_usage` only skips registering in `_active_sessions`, which doubles as on_ams_change's "skip the remain% weight sync" flag. ⚠️ A slot that empties mid-print is a RUNOUT — `on_ams_change` won't unlink its `SpoolAssignment` while the printer is `RUNNING`/`PAUSE` (read from printer state, not `_active_sessions`). ⚠️ Plate authority stays `PrintArchive.plate_index`; never copy it into the session row. ⚠️ The unassign endpoints do NO accounting (delete the row + `spool_assignment_changed`); the assign side is the accounted path — the tracker's «an assignment created after print start wins over the start snapshot», `note_assignment_change`, and the dialog's mid-print prompt — so replacing a slot's spool in one step (2026-09-13, *Replace spool* on the hover card) runs the same code as unassign+assign and skips nothing.

## Spoolman no-3MF tracking

For "Untitled" prints with no `.gcode.3mf`, `spoolman_tracking.py` snapshots each AMS slot's `remain%` + `tray_uuid` at start (`_snapshot_tray_remain`) and writes consumed grams from the drop × curated reference weight — only for slots the 3MF didn't cover, skipping mid-print-swapped slots. Tracking rows store `filament_usage=[]` (not NULL) for this path; all readers use `filament_usage or []` — keep that contract.

## An advertised AMS profile is not the spool (m175)

`Printer.ams_policies.backup_compatibility` lets a printer be TOLD a canonical colour and/or the Generic family of a base material for manually assigned spools, so firmware auto-refill groups them. The projection lives in ONE place (`services/ams_backup_compatibility.py::project_slot_assignment`) and reaches the wire through ONE publisher (`services/slot_assignment_publish.py::publish_slot_plan`) from all three inventory paths (internal assign + replay, Spoolman assign, Spoolman link — the two Spoolman routes share `services/spoolman_kprofile_link.py` for the K-linked family); the manual `configure_ams_slot` stays literal. Everything that reasons about the SPOOL — `get_feed_snapshot`, both loaded-filament builders (`print_scheduler._build_loaded_filaments`, `auto_queue_ams.build_loaded_filaments`), the status payload's per-tray `actual` (both shapers: `printer_state_to_dict` for WebSocket, `routes/printers.py::_build_printer_status` for REST), the frontend's `buildLoadedFilaments` — reads `services/ams_advertised_overlay.py`: an in-memory record written only after a successful publish, effective only while the live tray still equals what we advertised (dormant otherwise, never deleted by a reader), forgotten on unassign / auto-unlink / inventory-mode switch, and rebuilt once per printer on its first AMS push after a restart (`ams_backup_compatibility_apply.rebuild_once` — never in `lifespan`, where neither printer state nor the Spoolman client exists yet). Everything that reasons about the FIRMWARE — client-side backup-group reconstruction (`computeBackupGroups`) and the PrintModal remain-pool key (`groupTraysForBackup`) — deliberately reads the LIVE/advertised fields. ⚠️ Routing's two STRICT checks are the exception (owner, 2026-09-30): a forced colour and a strict profile compare with what the operator DECLARED (`FeedSource.declared_color` / `declared_variant`, read through `rule_color` / `rule_variant`; frontend `amsHelpers.declaredColor` / `declaredTrayInfoIdx` over `advertisedColor` / `advertisedTrayInfoIdx`; the offline wake step through the printer's canonical colour), and so does colour ranking — a backup group built from leftovers outranks the job's «exact» box. Base material, archive colour, attribution, `filament_low` and preheat stay on the spool. Applied overlay entries enter the feed snapshot's `revision` (sorted), so the latch key and the auto-queue placement check see them. RFID slots (valid tag on the live tray OR the spool) and external slots are never projected; the two hardware-decided knobs (`GENERIC_BASE_MATERIALS`, `GENERIC_MODE_KPROFILE`) live only in the policy module and change only with a capture on P1S+AMS and X2D+AMS 2 Pro. Bulk re-advertise (`POST /printers/{id}/ams-policies/backup-compatibility/apply`) previews with `dry_run`, refuses while printing (409) and without printer state (400), and its `revert` action re-publishes the actual plan for a slot the policy no longer projects — the same button rolls back after the policy is switched off. `filam_bak` is the only proof a group formed; an `ams_filament_setting` ACK proves acceptance only.

## A slot "matches its spool" when it shows the type WE wrote, not the material column (upstream #2902, 2026-09-24)

A non-RFID assignment's fingerprint is the slot BEFORE our `ams_filament_setting` (`assign_spool` snapshots it first), so the first AMS push after every such assign differs from it and the link survives only through `on_ams_change`'s "tray matches the spool" check. That check asks `routes/inventory.tray_types_written_for` — the slot plan's `tray_type` (family type, or the generic family's when the spool has none) plus the material — through `spool_slot_plan`, the SAME computation `apply_spool_to_slot_via_mqtt` publishes from. Never compare with `spool.material` alone: `PLA-AERO` ≠ `PLA`, and a family-less "PLA Matte" spool is written as `PLA`. Vault: `40-invariants/inv-slot-matches-what-we-wrote.md`.

## A spool without a family keeps ITS type on the slot; only the profile is borrowed (upstream #2902 / 88e8ca81, 2026-09-25)

When `build_slot_assignment` has no family (a Spoolman spool without a linked K-profile, a quick-added or legacy one — and the P*→system degrade on a printer without user presets), `slot_assignment._stand_in` asks `utils/filament_catalog.family_for_material`: a family whose name the material IS, else the family of EXACTLY the type the name states (`material_type`: words joined with a hyphen, the longest join that is a catalogue type, routing equivalences applied — "PLA Aero" → PLA-AERO → Bambu PLA Aero; PLA+ / "PLA Matte" → Generic PLA), Generic first, else the catalogue's own (Bambu Lab first). A name that is no known type ("ASA-GF") borrows the BASE generic's profile and keeps the spool's type as given. ⚠️ Never configure a slot from `generic_family_for_material`: it cuts the name at the first hyphen/space and the old code took that generic's TYPE too, so PLA-AERO went out as PLA — and routing compares nothing but the slot's `tray_type` under the default base-material matching, and AMS Backup groups by the profile. `resolve_raw`'s material-name fallback answers through the same function (it is what a spool save persists as `filament_family_id`). Authoring and the backup-compatibility policy keep `generic_family_for_material` — they ask for a base to inherit from, a different question. Vault: `40-invariants/inv-a-spool-without-a-profile-keeps-its-type.md`.

## A spool sits in one slot and leaves it only on proof

Every assignment writer removes the spool's other slot rows (`services/spool_single_slot.py`; journal and sessions untouched) and refuses (409) when the old slot feeds a running print — with no known session mapping every slot of a printing printer counts. No UNIQUE constraint: existing duplicates settle in `on_ams_change`, where the tag can be read. A presence bit that goes off on an IDLE printer does not unlink at once: `slot_unlink_hold` keeps the row ~25 s and drops it only if the slot is still empty (one glitch push used to leave the next print charged to nobody); auto stock loading treats a held row as leaving only when the slot shows another type or colour. An AMS that disappears whole leaves the card and the Virtual Printer and KEEPS its assignments. A spool with usage history, an assignment, an open print event or a session is archived, never hard-deleted (409) — the rule keeps the history, not the number. The number is never handed out again: `spool` is an AUTOINCREMENT table since m261, whose counter starts above every number the frozen registry (`core/spool_id_bound.py`) still finds, and the counter survives the SQLite↔PostgreSQL move and the portable backup (`core/pg_sequences.py`, `db_portable._source_id_bounds` / `_carry_id_counters`). A CSV import (C32) keeps a file's number — and the label identity with it, while no other spool has it — only above everything the counter has handed out (`spool_csv.highest_spool_number_given_out`), decided again under the spool table's write lock (`hold_spool_numbers`: SQLite's writer, PostgreSQL's table lock) and inserted first, after which PostgreSQL's sequence is raised past it (`persist_import`); a number given out before, also a deleted spool's, gets a new one. Vault: `60-specs/c047-spool-id-never-reissued-spec.md`. Vault: `40-invariants/inv-a-spool-sits-in-one-slot-and-leaves-it-on-proof.md`.

## A Spoolman spool printed with is archived, not deleted (C047 part 2)

The one door is `services/spoolman_delete.py` — single and bulk delete call it, nothing else sends a Spoolman `DELETE`. It refuses (409, no `DELETE` sent — the checks before it may read the spool) a spool that BamDude's history of the CURRENT Spoolman source says was printed with (`spoolman_usage_history.belongs_to`), one in a slot a print still to be charged feeds from, one a running print's final charge could resolve by a tray tag (`spoolman_tracking.guard_tray_tags` — every recorded tray plus the external holders 254/255; `attribution_tray_tag` is the ONE rule the charge writer shares), and one an open print's journal names. Its proofs are taken before what they guard and compared by ONE synchronous admission (`_try_admit`): the source generation G0 and a free source guard (`services/spoolman_source.py`), the activity revision A0 with nothing open (`services/spoolman_activity.py`: the accounting window opened first in `main.on_print_complete`, the first facts of a print, Git's SPOOLS category), the live slot state, and the number's fence revision F0 (`services/spoolman_binding_fence.py`). The admitted task belongs to the runtime — a cancelled request never stops it — and runs the `DELETE` with its own client built on the snapshot S0; a 2xx is cleaned up locally under the source guard (slots except a feeding one, K links), an unknown outcome is said as it is and cleans nothing; a client that fails to close never replaces the decided outcome, and a bulk delete goes on to the next spool. The fence never waits, only refuses: a binding writer takes a ticket before the read that proves the number and enters before its DML; a tag mutation is marked in the client primitives, and a compound door owns its numbers for its whole interval (`tag_operation`); the fence moves at the admission AND at the release of a delete, so a ticket from inside a lease is stale after it; a number a create returns is proved against the ticket taken right before its POST, and a number the operation already owns is not judged again by an older batch ticket. A change of the source (the mode, the address, the history record) is owned under the source guard taken before the credential anchor (`services/spoolman_source_changes.py`): refused while a print is being charged, and a change of the database (a new address, `rotate`) refused while any print accounts in Spoolman — the flag is set in one synchronous step with the activity check BEFORE the fresh SQL read of the durable predicate, and first-evidence writers wait for it (owner, 25.11: no base change during a print) — before any lane they take; inside the same task the journal lock reuses that admission. A restart replay's writer publishes its own activity record before its task exists and ends it when the task is done, so a cancelled holder never leaves a write unprotected; a Spoolman number a replay read (the seed's snapshot, a held change) carries the base generation it was read under (`ReplayBatch.bindings_stamp`, `spoolman_source.base_generation`) and is written only under the same one — else as an unknown Spoolman spool, the built-in spool kept. Every journal row asks for the right to a Spoolman number in ONE place (`print_usage_journal._spoolman_fact` → `spoolman_activity.admit_for_transaction`): the writer's admission, or a record bound to its transaction — never a wait, since the caller may hold SQLite's writer; while a base change is in flight the row keeps its built-in spool and its Spoolman spool is unknown. The RFID doors (the built-in from-slot, the built-in inventory's AMS pass) are admitted before their lane. A door whose remote proof comes before its admission (the manual Spoolman slot assignment) reads a settled snapshot of the source first (`spoolman_source_changes.settled_snapshot`, the delete's S0 too) and checks it right after the admission and its slot-ledger write (`admitted_for`): a source that changed meanwhile is a retryable 409 `spoolman_source_changed`. The two slot ledgers hold the active mode only (no reader gates on the mode), so a change of the mode empties the one it leaves — inside `SourceChange.decide` (`clear_left_ledger`), never one route, for every door that writes the mode, each naming to its change the mode the row will hold: the Spoolman settings route (its whole body validated against `AppSettings` types before the change, and stored in the form the change was given — a raw JSON `true` was decided as Spoolman and stored as `1`, the built-in mode), the general save, the reset (the row it deletes reads as the default mode) and Git's settings category. Each refuses, before its change, text not every database can hold — an unpaired surrogate (neither), a NUL (PostgreSQL; refused on SQLite too, so a value means the same on both) — by ONE rule, `schemas/settings.storable_text` (Git skips such a key as invalid): refused only at the write, it failed after the change had forgotten the overlay and raised the generations. `test_spoolman_mode_writers_take_the_source_change.py` classifies each write of a `settings` row its scan can see that may be the mode, calls of the helpers that take their key from a caller included, and follows what the module's own statements bind: a name a function, or one around it, binds in its body is its own; a module-level name is a constant only when every statement binding it at module level is a top-level string assignment, and an import only when each imports the same thing; a module with a star import has neither; an alias of a helper, the model or its table is followed only as a bare name in its own module. It cannot prove that no other form exists; among what it cannot see are the model, its table or a row carried through variables into a function that does not name the model, the table under another spelling, another column of the row, SQL or a table name built at run time, a helper reached through a name built at run time, a class attribute or another module's name for it, and a binding the module's statements do not make (an imported module's attribute set from outside, a walrus in a definition's header). The whole-database restore is outside it so: it replaces the database below the scan (on SQLite the file, through the backup API; on PostgreSQL every table, by names read at run time) and asks for a restart. It empties it only after the slot-ledger writers in flight finished: every door that inserts a row of `spool_assignments` or `spoolman_slot_assignments` holds `spoolman_activity.slot_write` from before its mode check (a column read, `spoolman_source_changes.mode_on` — an ORM object the session still holds would answer with the value it loaded) to its commit, taken before its first-evidence admission and its lanes and with no write of its session pending — a door that waits for a change then holds no record the change's new address would take for a print's. The change sets its flag, new writers wait for it, and the change waits for the ones in flight: a door that takes the credential anchor first (the general save, the reset, Git) waits before that anchor (`SourceChange.wait_before_anchor`), after what it refuses without the anchor (the caller's role) — a refusal decided only under the anchor comes after that bounded wait and writes nothing; one that holds SQLite's writer or a serialising row lock when it decides is refused at once; a wait past a bound is the retryable 409 `spoolman_print_in_progress` reason `slot_writes`. The overlay of advertised profiles is forgotten after the change's last refusal, so a refused change keeps its rows and the overlay that describes them. No delete and no base change sees a slot-ledger write. `test_slot_ledger_writers_take_the_slot_write.py` pins every insert of either ledger to such a door, and the order of the record and the admission. A print's accounting tail (`report_usage`, `cleanup_tracking`) is one charge ownership (`services/spoolman_charge.py`): admitted before its first write, its own client and the snapshot's token carried to `record_print`; full restore and shutdown close the delete and charge gates together and drain both. Readers resolve the history source purely (`resolve_source`); only owners persist it, and the first token of an address raises the generation. Vault: `60-specs/c047-spool-id-never-reissued-spec.md`.

## A Spoolman binding names its spool by number and `registered`

A Spoolman number proves nothing: Spoolman hands the number of a deleted spool to the next one (a plain `INTEGER PRIMARY KEY` on SQLite), and another database behind the address reuses every number. So `spoolman_slot_assignments` and `spoolman_k_profile` keep, beside the number, the `registered` stamp of the spool the writer proved (`spool_registered`, m266) — Spoolman sets it itself at creation, in whole UTC seconds, and no client can set or change it; the API names no database. The rule lives in `services/spoolman_spool_identity.py` (`verdict`: `same` / `unknown` / `other` / `gone`, stamps compared as UTC instants; usage history's `belongs_to` reads stamps through the same parser). Every writer stamps the row it writes and, in the same transaction, `writer_proved`: a row or link of the number carrying another known stamp is refuted first (its own slot excepted), then the number's unstamped rows in BOTH tables adopt the proof — otherwise old K links stayed unstamped and resolved for the next spool given the number. A sync stamps only what it found by the tray's TAG; a spool it found by the binding's own number (`hint`, a tag-less tray) proves nothing, so the row is judged instead, inside the sync's own transaction and locks (`spoolman_slot_ledger._judge_by_hint` — never `drop_stale`, which would take the printer's lock again). Whatever writes something to Spoolman or the printer from a binding's number confirms it first: a print's tail (`ChargeCheck` — slot numbers by the row's stamp, journal numbers through the slot rows that name them at the end; one read per number per print), the weight sync, the drying stamp, the backup-compatibility walk (which only records; `bulk_apply` settles), the slot card's `GET`, and the K resolver (`resolve_spoolman_slot_kprofile` takes `spool_registered` with no default and drops links stamped for another spool). `unknown` (a row from before m266) adopts the spool it was confirmed against (owner, 2026-11-27: trust on first read); `other` and `gone` write nothing, the binding and the number's K links that are not the current spool's go (`drop_stale` / `refute`), and a print's tail sends `print_usage_spool_changed` on the missing-assignment event. While a printer's print accounts in Spoolman (`evidence_held`: a `printing` archive, its tracking row, or any completion's accounting window) its rows are that print's evidence — the journal number is confirmed through them at the end — so a reader only declines to write and that print's tail removes them. A change of the Spoolman database (a new non-empty address, `rotate`) removes every binding and K link inside `SourceChange.decide` (`clear_all`; Git's settings restore writes no address and the reset only empties it, so neither does); it waits for no slot writer, because a row committed after the clear carries the old database's stamp and is refuted at its first confirming read. The settings page saves the address only through its own button and a confirmation with what goes (`GET /settings/spoolman/address-change-preview`), never along with another field. Only Spoolman's own "no such spool" — a 404 whose JSON body carries `message` — is `gone` (`spoolman.says_spool_not_found`); a reverse proxy's 404 is Spoolman not answering and removes nothing. After its charges, a print's tail also goes over every slot row of its printer, a slot the print did not feed from included (`ChargeCheck.settle`, upstream 23d04c864): only while the printer reports no print — asked first and again under its assignment lock (`reports_no_print`), since a print started meanwhile keeps the rows as its evidence, for its own tail, and a gone number Spoolman gives to a new spool must not lose the row that refutes it — a number Spoolman says it no longer has is refuted as above, and one whose spool Spoolman reports `archived` — archived in Spoolman itself — is released (`release_archived_slots`), for the spool the row was proved for only (`same` or `unknown`), under the slot-ledger doors. Outside the rule: readers that write nothing from the number (routing, the history filter, diagnostics, lists), a number reissued in the middle of a print after the binding that froze it was changed by hand, and the non-atomic GET-then-write of Spoolman's API. Spec: vault `60-specs/spoolman-binding-identity-spec.md`.

## The remain% weight sync waits for the booking

No writer of a spool's weight from the printer's remaining-percent reading writes while a print on that printer still has filament to charge. One predicate, `usage_tracker.print_is_unbooked` — a registered session, OR the printer RUNNING/PAUSE (a restart may restore no session; Spoolman mode registers none), OR a completion in progress (`completion_in_progress`, one token per completion, gone in `finally`, dropped by the next start) — is asked by the automatic sync in `on_ams_change`, the Spoolman tagged-spool sync and both Sync buttons. The session leaves memory before the booking commits; a push in that gap wrote the remain% weight and the print's grams were added on top. The mark gates the weight sync only: it never changes what the tracker charges and never widens the K re-apply gate in `on_ams_change`. Both AMS-sync sites write through `sync_spool_weight_from_ams`, which re-reads weight and lock under the row hold and declines a stale decision — a weight typed by hand stands; unlocking is an explicit user action. Vault: `40-invariants/inv-weight-sync-waits-for-the-booking.md`.

## Refilling an inactive AMS slot is not another empty reel

`print_usage_journal.without_stale_refill_runouts` requires a prior autoswitch, an observed backup within the same four-slot AMS, a positively present different replacement at load and repeat, and no observed return to that source. A matching repeat has no accounting or archive authority: live recording resolves inherited spool identity before its gate and shares one frozen presence snapshot with insertion. Typed new/upgraded/duplicate/rejected outcomes keep repeats silent while preserving a confirmed pause-to-autoswitch upgrade. Live recording declines a stale refill before notification, and internal inventory, Spoolman, segmentation, purge and projection filter already-saved repeats through the same policy without rewriting the forensic journal. A real return re-enables the next runout; missing presence, other units/AMS-HT and external holders never acquire this proof by inference. ## The K-profile table is filed per nozzle diameter; the cache prunes only what a held table dropped (upstream #2854/#3044, 2026-09-24)

An `extrusion_cali_get` reply is the complete table for ONE diameter, and the printer answers whoever asks — BambuStudio on the same topic, the git backup's 0.2–0.8 probe, the spool dialog per fitted nozzle. `BambuMQTTClient._store_kprofiles` files each reply under its diameter and `state.kprofiles` is the union (a `get_kprofiles` waiter still receives only its own reply; the history view is filed the same way). ⚠️ `cali_idx` is numbered per nozzle AND per hotend, so nothing matches a live profile on the index or the name alone: the card's K goes through `utils/kprofile_lookup.build_slot_k_resolver`, shared by the REST and WebSocket shapers (the slot's own extruder first; an index-only fallback only when the candidates agree, fitted diameters as tie-break; an AMS the extruder map does not name is UNKNOWN, not extruder 0 — a deliberate divergence from upstream), and the bind / PA-tab link / note / audit lookups filter on `nozzle_diameter` + `extruder_id`. A spool holds ONE PA profile per printer / extruder / nozzle diameter / flow type — BambuStudio's identity for a PA profile — so the PA tab keys its selection through `spool-form/utils.ts::profileSelectionKey` (never a hand-built `printer:cali_idx:extruder` string), and the bind prefers the link of the flow type it is given. ⚠️ **Every binder asks `utils/slot_nozzle.slot_nozzle(state, ams_id, tray_id)` for the slot's extruder, diameter and flow** (`state.nozzles` is indexed by extruder id, 0 = right/main) — never `nozzles[0]`, never `getattr(state, "nozzle_volume_type", …)` (the state has no such field; that constant made every High Flow calibration unreachable, and `test_kprofile_bind_reads_the_slots_nozzle.py` scans for it). A printer that reports no flow class (X1C/P1/A1 name the nozzle by material) binds as Standard, which is how the sync stores its undeclared rows; Configure Slot filters by the fitted flow only when both the printer and the profile declare one (`resolveSlotNozzleFlow`). ⚠️ `sync_printer_kprofiles_to_cache` hard-prunes only rows whose diameter has a non-empty table in `live` — a diameter never read is unknown, and an empty answer stays ambiguous and prunes nothing. The fitted diameters are read once per connection when a push first names one (`on_kprofile_tables_due` → `printer_manager._prime_kprofile_tables`); the blind 0.4 prime on connect stays. ## The spool name template is display only (owner, 2026-09-26, audit D3)

The user edits `spool_display_template`, so it decides how a spool is NAMED and nothing else — no search, filter, match or migration may lean on the template or on its default text. Spool search is the fields OR the composed name, built once in `inventory_service.spool_search_filters` (Filaments list and the slot-assignment picker); the composed name only ADDS matches that span fields. `inventory_service.spool_display_template(db)` is the one reader of the setting — `test_no_route_reads_the_naming_setting_raw` fails on a route that reads it raw. The default lives in three places that must agree: `schemas/settings.AppSettings`, `inventory_service.DEFAULT_SPOOL_DISPLAY_TEMPLATE`, `frontend/src/utils/spoolName.ts`. Stored templates are never rewritten: a migration matching the old default text would be logic tied to the template. The name orders spools in two places only, both the owner's: as a level of the operator's spool order (2026-11-15), and as the tie-break of a column sort when the template shows the spool number (2026-11-27) — spools the column leaves equal then follow their composed name (the number padded, so #2 comes before #10), otherwise their number, ascending either way (`inventory_service.spool_tiebreak`, mirrored by `InventoryPage.compareSpools`). ## The slicer, the bed plate and the presets are chosen through one family, `components/slicing-setup/` (2026-11-20)

The Slice dialog, both filament-calibration pages (`calibration/CalibrationSlicingSection.tsx`), Assemble project's rows and the filament-family dialog's "From an existing preset" compose `PresetSelect`, `PresetFilters`, `PresetListStatus`, `PipelineSelect`, `SlicerChoice` and `BedPlateSelect` over one catalogue query (`usePresetCatalogue`), one choice state (`choiceState`, a `POLICIES` entry per place) and one filter hook (`usePresetFilters`); the "my preset" rule is `utils/presetPickerUtils.ts` alone (imported, every Orca Cloud profile, own Bambu Cloud presets). A soft filter narrows what a list offers and never changes a choice; each field relaxes only the filters needed to show a matching profile and explains which ones it relaxed. The printer list prioritizes the configured farm model and nozzle over the selected source. The filament list prioritizes the selected source over loaded filament. After relaxing a filter, the field restores any other filter it can satisfy. Automatic process/filament picks apply every active filter unrelaxed, the printer's automatic pick none. A choice made by a person, a saved set or a record is never replaced by an automatic pass; what a gone choice does is the place's policy. A request (slice, save a set, calibration start or download) carries only refs the CURRENT catalogue lists, asked again right before it is sent — never only when the form opened; the loaded filter reads the selected printer's own source lineage. Never draw a preset `<select>`, a slicer card, a bed-type cast, a filter setter or a catalogue refresh outside the family: `__tests__/components/slicingSetupOwnership.test.ts` fails on it. K profiles, calibration save, history and slot binding are not the family's (owner). Vault: `40-invariants/inv-one-slicing-setup-family.md`.

## A preset is found by its identity, and one the slicer cannot resolve refuses the slice (G12)

The sidecar (our `orca-slicer-api` fork) indexes each profile category by the `name` FIELD — never by composing `<name>.json` — so presets in vendor subfolders and with "/" in the name resolve; a name two files share is ambiguous and an error naming both, never "the first one". A printer / process / filament preset whose `inherits` chain cannot be completed is a structured 422 (`preset_unresolved`) the backend turns into a translated refusal — the slicer's built-in defaults are never a fallback. A printer profile is "renamed" (flattened to its stock parent for the CLI) only when its own name is NOT a stock preset's. The sidecar reports a code version on `/health`; the backend's `REQUIRED_SIDECAR_VERSION` makes the Slice dialog ask for a container rebuild — a sidecar change is a fork push + rebuild, and bumps both. In the backend, list options of a profile (which Orca Cloud may send as ONE quoted string) are decoded by `utils/slicer_strings.py` for every reader; a preset's material comes from the family catalogue by its setting id, not from its name; presets of different sources with one name are never merged, deduped or resolved across sources by name (the Slice dialog's lists, the parent of a renamed printer preset, the filament a project file names). In the dialog a choice made by hand is explicit: no automatic pass replaces it while the listing has it. "Loaded filament" for the dialog's farm filter is the feed snapshot's spool, never the advertised profile. Vault: `40-invariants/inv-preset-identity-and-unresolved-refusal.md`.
