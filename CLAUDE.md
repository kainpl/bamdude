# CLAUDE.md

Guidance for coding agents working in this repository. Claude Code reads this
file on its own; `AGENTS.md` points other tools here. Everything below is about
the codebase — how it is built, what must not be broken, how a change is done
end to end — and none of it is Claude-specific. A maintainer's personal context
(local checkouts, knowledge-base wiring, paused work) lives in `CLAUDE.local.md`,
which is not in the repository.

## Project

BamDude — self-hosted print archive + farm management for Bambu Lab. Hard fork of Bambuddy. Python 3.12 / FastAPI · React 19 / TS / Tailwind 4 · SQLite or PostgreSQL · MQTT · aiogram 3.x. en+uk locales.

## Knowledge base

Architecture rationale, rejected alternatives and the "why" behind every
invariant below are recorded in a separate Obsidian vault (`bamdude.obsidian`,
maintained alongside this repo and not public). The `Vault:` pointers in this
file are paths inside it — for the maintainer. The record a contributor can
read is: the Key Invariants below, each migration's docstring,
`CONTRIBUTING.md`, and `CHANGELOG.md` — the changelog is written as prose that
says what changed and why, not as a commit list.

A code graph of the repository (functions, classes, cross-file relationships,
community structure) is attached to every release as
`bamdude-code-graph-<version>.json.gz` (plus a `.report.md` overview). With
[graphify](https://pypi.org/project/graphifyy/) installed, gunzip it to
`graphify-out/graph.json` at the repo root and `graphify query "<question>"`
returns a scoped subgraph — usually far smaller than a grep across the tree;
`graphify update .` refreshes it after your edits without any API key.

⚠ **Slicer sidecars** — `cd slicer-api && docker compose --profile all build && docker compose --profile all up -d` (health :3001 bambu, :3003 orca). Two traps, both silent: the build context is the fork's **GitHub URL**, not the local checkout; and the version lives in **both** `docker-compose.yml` and `.env`, where `.env` wins. Details: vault `10-repos/orca-slicer-api/slicer-docker.md`.

⚠ **Run backend tests from the repository root.** The camera supervisor spawns `python -m backend.app.worker_guardian`, which must import `backend.app`. `conftest` sets `BAMDUDE_IGNORE_DOTENV`, so local `.env` does not affect tests. Cameras are worker-only; `CAMERA_RUNTIME` has no effect. Do not override `DATABASE_URL`: database-mode tests rely on its normal resolution. Use `--timeout` so a hung test produces a named failure.

⚠ **`npx tsc --noEmit` is a silent no-op here.** The root `tsconfig.json` is `"files": []` plus project references, so without `-b` the compiler enters no file and exits 0 on anything — including a file whose only line is `export const x: number = NOT_DEFINED_ANYWHERE;` (measured 2026-07-28). Always `npm run typecheck` (`tsc -b --noEmit`). A refactor that dropped an import passed a bare `tsc` run and surfaced only as a blank dialog under vitest. ⚠ The pre-commit hook checks the **app** project only (`tsc -b tsconfig.app.json`, ~43 s, keeps commits fast); `npm run typecheck` also enters `src/__tests__` — run it before claiming green. Since 2026-09-04 the root references `tsconfig.test.json` too, so `src/__tests__` is type-checked as well — the run costs ~2× (a second full program over the same `src` graph), and a fixture that has drifted from its wire type now fails the check instead of only vitest.

## Architecture

**Backend `backend/app/`:** `main.py` (FastAPI factory + lifespan + global state dicts `_active_prints`/`_expected_prints`). `api/routes/` (every router registered in `main.py`). `services/` (printer_manager, bambu_mqtt, telegram_bot, notification_service, background_dispatch, archive, virtual_printer/, obico_detection). `services/telegram_handlers/` (aiogram FSM + `auth_middleware.py`). `models/` (async SQLAlchemy) + `schemas/` (Pydantic). `core/` (config, database, auth, permissions, encryption, rate_limit, websocket). `migrations/m000_*..mNNN_*` auto-discovered. `i18n/` + `data/` (en/uk JSONs: `telegram_ui`, `notification_templates`, `maintenance_types`).

**Frontend `frontend/src/`:** React 19 + Router 7 + TanStack Query 5. `api/client.ts` is **fetch-based, NOT Axios** — single `request<T>()` helper; binary endpoints call `fetch` directly. `i18n/locales/{en,uk}.ts` keys must match. Three.js for 3D viewer. **Production bundle tracked under `static/`** — source + bundle ship same commit.

**DB:** SQLAlchemy 2.0 async (aiosqlite/asyncpg). SQLite: WAL + 15s busy + NORMAL sync. `init_db()` = `create_all()` + pending migrations. `DEBUG=true` re-runs latest migration on startup.

## Migrations

Startup: `init_db()` → legacy `bambuddy.db` rename → `Base.metadata.create_all()` (idempotent) → SQLite→PG auto-migrate (if PG empty) → `_ensure_migrations_table` → `_bootstrap_existing` (marks m000+m001 applied for legacy) → `_run_pending` → `conform_imported_schema` (only after an import in this process).

⚠️ **The SQLite→PG move imports the file AS IS at ITS migration level, `_migrations` included, and the chain resumes at N+1** (`db_portable._reflect_sqlite_schema`; 2026-09-09). Never build the target schema from `Base.metadata` before the load — the models lack exactly the legacy columns/tables the later converters read (m157 `printer_id`, m158 project pivots), and re-running the whole chain on PG is how a dialect bug in an old migration reached a tester while the maintainer's own SQLite→PG path never executed it. What no migration ever did on SQLite (FK rules, NOT NULL, UNIQUE, CHECK, m001's tsvector half) is added once, after the chain, by `conform_imported_schema` — never on an ordinary boot. Model columns marked `info={"migration_shim": True}` (notification.py) are not canon and are skipped there. Vault: `40-invariants/inv-sqlite-move-imports-file-as-is.md`.

Each `mNNN_*.py` has `version`, `name`, `async def upgrade(conn)` (DDL), optional `async def seed(session_factory)` (DML). Helpers in `helpers.py`: `add_column`, `column_exists`, `table_exists`, `recreate_table`. Per-migration rationale lives in migration docstring — read there, don't duplicate here. Two branches can each take the same next number; `tests/unit/test_migration_versions_are_unique.py` fails when two files share a `version` or a file's number is not its `version` — renumber the unreleased one.

**Adding a column = TWO places:** model file (fresh installs via `create_all`) + new migration via `add_column()` (existing DBs).

## Key Invariants

**Local microservices report their work through the parent log.** The parent runtime that owns a child process/RPC logs service readiness, loss and restart, then wraps each meaningful operation with a start and terminal outcome (success, failure, timeout or cancellation), elapsed time, a correlation ID and a safe result summary or sanitized failure reason. A child's stdout/stderr may only reach a bounded diagnostic buffer; an HTTP 200, queued task or `health=ready` is not proof of completed work. Aggregate hot paths such as camera frames, scan pages and polling instead of logging every event; never log credentials, raw payloads or sensitive paths. Verify success and failure visibility in the parent logger with a real worker test. Vault: `40-invariants/inv-local-microservice-parent-log.md`.

**A part-render attempt is over only when its process tree is proven gone (E3).** The disposable `part_render` is the only reader of a library file for rendering: it opens, hashes and streams the file and starts Node in its own process group / Job Object; main and `part_render_service` never `stat`, `resolve` or open the path. Every process of an attempt is recorded by its PARENT — `<name>.launch` (a one-off token the parent also puts on the child's command line, `launch_arg`) before the spawn, `<name>.pid` (`pid` + start + the boot it ran in) before the child gets any input (`services/part_render_tree.py`) — and the worker answers a run only after `PreviewProcess.stop()` and `tree_gone` prove the tree gone. Main's one slot (`PartRenderRuntime.render`, an `asyncio.Lock`) is held through the reply, the cancel and, failing that, the retire with the same proof (`strict=True`) over every attempt in the worker's staging — which also covers a tree orphaned when the worker itself died. An unproven tree, or a start whose cleanup proved nothing (`SpawnUnproven`), makes the runtime `ownership_uncertain` until a restart and no replacement worker starts: a retry never runs beside a reader still hung on a NAS. An EARLIER run is proven over by its records — never by a bare negative scan of the process table (a child born as its parent exits slips past any scan): a generation records its owner (main), its worker guardian and the worker beside its attempts, and `part_render_tree.generation_gone` needs that main dead (never killed — a live one is another main), then every recorded process ended, killed if need be, PARENTS FIRST. A launch without its record is ENDED, never trusted to read EOF: once its parent is positively proven dead nothing new can take its token, so every holder of it is killed and waited for until a scan finds none — and of the parent's token too, because a fork caught before its exec still runs the parent's command line; an unreadable token is no proof. A command line is public, so a holder positively of another user (the uid POSIX shows for every process — one only when real, effective and saved agree, since none of ours changes uid, so a setuid `sudo` of the same user is someone else's; the user name where Windows shows it) is a stranger that read the token, never signalled and never able to keep the run unproven — and carrying the token is no authority to signal: a holder is killed only when its user is READ and IS the run's owner, while a hidden identity, or a run whose owner names none, keeps the run unproven and the holder untouched. Only such a POSITIVE observation excludes a process — psutil answers `None` for what it may not read, and `None` is not absence: a process that may be ours and whose command line cannot be read keeps the run unproven (on Windows a process running another image, or started by the kernel, is positively not ours — the image name and the creator are shown for every process). A record names its boot: one of another boot has ended and its pid is never signalled, and a run whose owner names another boot is over whole, whatever a power cut left of its files — a persisted boot counts only in its platform's format (what the reader writes: a UUID, a `bootid-<DWORD>`), any other text is no boot at all. A pid and a start identify a process only within one boot, so a record matching a live process is acted on only when its boot and this one are both known and equal — an unknown boot signals nothing, on every platform; `tree_gone`'s records are this run's, so this boot's by construction. The one process outside every token is main's own fork caught before it executes the worker guardian, which can only read EOF where its bootstrap should be and exit. An error in that proof closes admission and restore; without a scheduler, restore asks for a completed proof (`earlier_proven`). A proven earlier run's staging is removed. A restore asks `scheduler.stop("restore")` first — one shared stop, its proven answer — and refuses (409) without the proof. `plate_renders` / `plate_render_objects` / `part-renders/` have one writer, `services/part_renders.py` (guard test); every transition is a CAS on the full key and the scheduler's generation. ⚠️ What an untrusted plate makes the child hold is bounded: a top/pick image is measured from its PNG header (PNG only) before it is decoded, the marker scan keeps only the selected ids. Vault: `40-invariants/inv-part-render-attempt-proven-over.md`.

**A part's picture has one writer, one reader, and its name → part mapping is decided at read time (part thumbnails E4).** `services/part_images.py` alone writes `product_parts.image_*` and the photos under `products/<id>/part-images/` (`tests/unit/test_part_images_have_one_writer.py`), and alone answers which picture a part shows (`resolve`), the editor's state and the candidates. Nothing caches a resolution: instances come from the file metadata on every read (`product_composition.plate_objects` → `part_names.tally_objects` → `part_index`), so a merge, a split or a new alias changes the picture without a write; a pin that no longer holds falls back to auto and says why (`file_unlinked` / `file_trashed` / `object_gone` / `not_this_part` / `not_rendered`), never re-pins itself. Every route whose answer carries a shape of `part_image_shapes()` is decorated `@part_images.attach` and fills the pictures in one read per kind — the parts', and the plate objects' when there are any — best effort, in a savepoint: a lookup that fails leaves the pictures out, never the route's write (`tests/unit/test_part_image_shapes.py` walks every schema and every route). The WebSocket event `part_images_changed {product_ids}` goes after the ROOT commit only — `mark_changed` collects on the session, a rolled-back savepoint takes its own marks and files with it; the render writer reports through `mark_renders_changed` in its own transaction, and only a transition that moves a plate's status or result, never from a background session (in the tests every session shares one connection, and closing any of them rolls back everyone's work). Every file operation of the writer runs through `preview_artifacts.disk`, which a cancelled caller still waits for, and is all-or-nothing: a photo or a copy that does not get its name leaves no file, even when the caller catches the error and commits. A photo is never stored as sent: its orientation goes into the pixels and it is saved again in its own format with only its colour profile, so EXIF (GPS, the camera's serial), XMP and comments never reach the readers of orders and stock or an export — and what was saved must fit `attachment_limit()`, the cap the import asks of it (413 otherwise). An imported pin is kept only when it holds on the new farm (in the columns' range, a linked plate, an object of this part) — its pixels come later. Vault: `40-invariants/inv-part-image-resolved-at-read.md`.

**Auth always-on.** Every endpoint via `RequirePermission(Permission.X)`. Setup-gate middleware returns `503 setup_required` until `POST /auth/setup` creates admin (whitelist: `/auth/status`, `/auth/setup`, `/system/health`). API keys (`X-API-Key` / `Bearer bd_...`) bypass JWT but satisfy perms. New keys are `bd_…`; Bambuddy's `bb_…` stays accepted forever (only the hash is stored, so an issued key cannot be renamed). The prefix only tells a Bearer key from a JWT, and `core/auth.is_api_key_token` is the one place that asks — `tests/unit/test_api_key_prefix_is_asked_in_one_place.py` fails on a hand-written `startswith("bb_")`. Recovery: `python -m backend.app.cli reset_admin`.

**JWT + sliding refresh.** Access JWT has `jti` + `iat` (1h TTL); `/logout` revokes via `auth_ephemeral_tokens`. Password change stamps `user.password_changed_at` — older `iat` rejected. Refresh: SHA-256-hashed, HttpOnly + SameSite=Lax + Path=/api/v1/auth (`bamdude_refresh`), Secure auto from scheme, rotating with `family_id`; reuse collapses family. Frontend auto-retries 401 via `/auth/refresh` (coalesced).

**2FA + OIDC.** TOTP + email OTP + 10 backup codes. Login returns `requires_2fa=True` + `pre_auth_token` when enabled. OIDC: PKCE S256 + state + nonce + JWKS; SSRF guards reject non-HTTPS/loopback/private/link-local. TOTP secrets + OIDC `client_secret` Fernet-encrypted; `MFA_ENCRYPTION_KEY` auto-bootstraps (env → `DATA_DIR/.mfa_encryption_key` → generated, mode 0600). Backup ZIP packages key alongside DB.

**Rate limiting.** Sliding-window in `auth_rate_limit_events`. Login 10/15min per user + 20/15min per IP. Behind proxy: set `TRUSTED_PROXY_IPS`.

**Permissions.** `resource:action` (`printers:control` etc.) in `core/permissions.py`. Default groups: Administrators / Operators / Viewers. **API-key scopes** confine a key's reach: `core/auth.py` maps every `Permission` either to a `can_*` column in `_APIKEY_SCOPE_BY_PERMISSION` (`can_manage_library`/`inventory`/`projects`/`archives`/`maintenance`, `can_queue`, `can_read_status`, …) or onto `_APIKEY_DENIED_PERMISSIONS` (admin-only — e.g. `ARCHIVES_PURGE`/`LIBRARY_PURGE`/`PIPELINES_WRITE`). **Every new `Permission` MUST land in exactly one** (a drift-guard test enforces it) **and be seeded to Administrators in its migration** (O2 discipline — Administrators aren't self-healed at startup, our migrations are frozen).

**The Workshop's rights are four domains and one filing right, asked in one place (WS-13 E13 §O, m194).** Sixteen permissions — `orders:read/create/update/delete/file_prints`, `products:read/create/update/delete`, `customers:read/create/update/delete`, `stock:read/move/adjust`; `projects:*` and `stock:manage` are gone, with no runtime fallback (the group editor refuses the old keys). m194 maps them; m046's `_CARRIED_FORWARD` keeps the four `projects:*` keys alive until m194 runs — the owner's one exception to frozen migrations (N14), never a precedent. Filing a PAST print is `F(print)` = `orders:file_prints` ∨ (`orders:update` ∧ that print's `archives:update_all` / `update_own`); NEW work under an order (print dialog, queue, reprint, clone, the plate's «Repeat», Telegram) is `Fф` = `orders:file_prints` ∨ `orders:update`. Both are answered by `api/routes/_workshop_rights.py` (`ensure_may_file`, `ensure_may_file_future`, `may_file_future`) and the link itself by `order_filing.resolve_link` (an open order, else 409 `order_closed`; a line of that order); a copy for someone without `Fф` goes `without_order` / `keep_order=false`, and the button says so before it is sent. Never hand Operators `archives:update_all` for filing — it opens everybody's photos and files (upstream security #5). Past prints move through the order's commands (`add-archives` / `remove-archives`; `PATCH /archives` keeps its binding fields under the same checks), and every exit locks the order rows, then the print, then the parts' ledger (lock class PRINT, `archive_write_scope(first=…)`, `lock_prints`): C1 — a print whose output the order received never leaves — is read under the order's lock, and a print in the trash is refused whole-batch (409 `print_in_trash`), never filed and never skipped. A write that changes the Workshop from another section asks that domain's own write too, through `core/auth.RequestCredentials` (`request_credentials` + `creds.check(gate)`, which honours an API key's scope, never a hand-written permission test): linking or unlinking files and folders to products, and a move that changes a file's set of products (compared before anything moves; a batch with one such file is 403 and nothing moves), ask `products:update`. Taking from stock (explicit numbers, `auto`, «Take from stock») is `stock:move`; the consequences of an order edit (release on cancel, completion, a lower quantity) need no stock right; write-offs are `stock:adjust`; a delete asks the rights of its real consequences (O24). Reads are masks, not page gates: `workshop_view()` — bound per request by `bind_workshop_credentials` on every router that reads it — nulls another domain's fields, and a filter or sort on a hidden field is 403 `workshop_read_required`; `customers:read` sits in the `can_manage_projects` key bucket (contacts are personal data); a dispatch note's recipient snapshot needs `customers:read` ∨ `stock:move`, else a minimal row and 403 `dispatch_note_restricted`. A file an order names (`from-files`, a plate line) must be visible through `library_name_scope` + `file_name_visible`; someone else's and a missing one are the same 404. A folder's link to products is a standing rule its linker set: a file that lands in it (upload, slice, ZIP) inherits the link, and deleting the folder drops it, without asking `products:update` (owner, 2026-10-04). The UI only hides or explains the doors — one function per action in `utils/workshopRights.ts`, and `SectionLink`: a name into a section you cannot read is text, an action is absent. Vault: `40-invariants/inv-workshop-rights-by-domain.md`.

**An API key's printer list is enforced in the gate, not in the routes (`core/api_key_scope.py`).** `APIKey.printer_ids` — `None` every printer, `[]` none. The three gate factories (`require_permission` / `require_any_permission` / `require_ownership_permission`) take the `Request` and call `enforce_printer_scope` right after `authorize_api_key`, so no route can forget it; a caller that invokes a checker directly (`routes/monitor.py`) must pass `request=`. It reads printers BY NAME: `printer_id` / `printer_ids` / `queue_id` in the path, the query and **anywhere in the JSON body** (FastAPI parses and caches the body before it solves dependencies), plus `mqtt_printer_ids` (comma list, parsed exactly as the support route parses it); jobs via `source_queue_item_id` / `queue_item_ids` anywhere and, on `/queue/…` only, `{item_id}`, `{batch_id}`, `item_ids`, `items[].id`; and `_PATH_RESOLVERS` for things that belong to one printer (plug, maintenance item, dispatch job, calibration session). A value it cannot read as an id is REFUSED — pydantic coerces `"2"` and `2.0` to 2, so an unreadable reference must not pass; a name that resolves to nothing passes and the route 404s. `/auto-queue` is closed to a restricted key as a whole (the distributor picks the printer). Lists narrow themselves via `key_printer_scope(request)` / `in_key_scope` — printers, status batch, queues, queue items, monitor snapshot; history and statistics are NOT printer-scoped. ⚠️ A new printer reference under another name (`target_printer_id`) slips past the reader: `tests/unit/test_api_key_printer_scope_coverage.py` walks every key-reachable route and fails until the name is read or listed in `NOT_A_PRINTER` with a reason. Vault: `40-invariants/inv-api-key-printer-scope-in-the-gate.md`.

**Telegram dispatch authority is the chat (m045+).** `NotificationProvider` rows of `provider_type='telegram'` keep only `enabled` + `daily_digest_*` + token + name (+ `printer_id`). The 24 `on_*` flags + `quiet_hours_*` are forced True/False by m045 + `_coerce_telegram_provider_fields`. Per-chat `TelegramChat.{notify_events, quiet_hours_*, daily_digest}` is sole authority. **Never reintroduce a provider-level event toggle for telegram.**

**A telegram provider IS a bot, and one polling session holds them all (m180).** Every ENABLED telegram row is its own bot: one `Dispatcher`, one `_run_polling(dispatcher, bots)` task, `start_polling(*bots)` (aiogram runs a long-poll task per bot inside it and hands each handler `event.bot`). **Never a second `Dispatcher`** — the handler routers are module singletons aiogram attaches to one — and never a hand-rolled `getUpdates` loop. The registry is `telegram_bot._bots` (provider id → `Bot`) + `_bot_ids` (Telegram account id → provider id, from `get_me`); readers are `get_bot(provider_id)`, `send_message(provider_id, …)`, `send_photo(provider_id, …)`, `provider_id_for_bot`, `running_bot_provider_ids`. A token whose `get_me()` fails costs only its own provider a bot (the error goes to that row's `last_error`); the rest start. **A bot token belongs to ONE telegram row** — a 409 at create/update, m180's `dedupe_tokens` for what was already stored, and a start-time backstop (oldest polls) — because Telegram serves one `getUpdates` per token. The lifecycle stays behind one `asyncio.Lock` (`start`/`stop`/`restart` end to end, `restart` across both halves, the registry detached before the first await, bounded shutdown); a provider save restarts the session only when `current_bot_providers()` — every enabled row as `(id, token)`, `ORDER BY id` (unordered is heap order on PostgreSQL, which an UPDATE moves) — answers differently. **A chat is the PAIR `(provider_id, chat_id)`**: Telegram's private chat id is the person's user id, identical in every bot, so the same person in a second bot is a second row with its own role and scope. `telegram_chats.provider_id` is NOT NULL; two writers only — the middleware at registration (from `provider_id_for_bot(event.bot.id)`, never "the first telegram provider") and `POST /telegram/chats` (the provider named, else the only one, else 400 / 409). There is deliberately NO re-bind on contact. Auto-registration's "first setup" is per bot; `telegram_registration_open` stays global. Every fan-out to "a provider's chats" filters on the column (`_send_telegram_to_chats`, `_send_telegram_digest_to_chats`, `_has_telegram_digest_subscribers`, `_send_telegram` all take `provider_id`); per-chat module caches key on `(bot account id, chat id)`. Deleting a telegram provider removes its chats **in code** (SQLite runs no FK actions; the CASCADE is the PostgreSQL backstop). Vault: `40-invariants/inv-telegram-chat-belongs-to-its-bot.md`, `40-invariants/inv-one-telegram-poller-per-process.md`, `60-specs/telegram-multi-bot-spec-plan.md`.

**Macros.** GCode via MQTT `gcode_line` wrapped with `M1002 gcode_claim_action:0/idle`. `services/macro_executor.py` + `PrinterManager.execute_macro_and_wait`. Swap macros fire by themselves: `swap_mode_start` from `background_dispatch` before `start_print`, `swap_mode_change_table` from `on_print_complete` (and `print_reconciliation`'s recovery). A model is swap-capable when a profile in `core/swap_profiles.py` names it — the printer form and the saved print profiles ask that catalog, never a list of their own; a new mod is a catalog entry plus its two built-in macros seeded by a NEW migration (m005, m192), whose G-code carries no `gcode_claim_action` of its own. `action_type='mqtt_action'` (m017+) routes via `core/mqtt_macro_actions.py` + `services/macro_trigger.py`.

**Single dispatch layer.** Only `background_dispatch` runs prints. `print_scheduler._start_print` is a thin wrapper. Dispatcher creates exactly one archive per physical print, wires `PrintQueueItem.archive_id` in same txn, signals via `PrintDispatchJob.completion_event`. External prints (printer screen / Send-to-Printer) create their archive in `on_print_start`, at print start — see *The archive row is created at PRINT START* below.

**Archived printers (soft-retire, m105).** `Printer.archived` + `archived_at` — an INDEPENDENT axis from `is_active` (Maintenance Mode): maintenance parks temporarily + keeps the card visible; archive retires + hides everywhere, history preserved. **A queued job owns its bytes, and the spool is one writer (m173).** After capture, nothing on the print path reads the library file, the archive or the share again — it reads the job's snapshot. `queue_sources` holds **one row per distinct content, never per job**: the key is the SHA-256 of the bytes that were actually captured (`UNIQUE` + a named `length(sha256) = 64` CHECK), the file lives at `DATA_DIR/queue-spool/objects/<aa>/<sha256>.<ext>`, and a half-written capture sits in `queue-spool/staging/<token>.part` with **no row at all** — so "being prepared" is not a state the table can be in. The refusals are a closed taxonomy answered verbatim — `503` `source_copy_busy`, `422` unreadable / changed / not a valid container, `504` timeout, `507` out of space — and no route invents a status beside them. ⚠️ The archive keeps the two hashes apart: the **unpatched** snapshot is the archive's source, the patched artifact is what was dispatched, and a snapshot never creates a `PrintArchive` by itself. ⚠️ SQLite ignores `ondelete`, so detaching a source from its jobs is done in code. **Dispatch is claimed per PRINTER, not per item.** `set_queue_busy()` flips `PrinterQueue.status='printing'` and `print_scheduler` seeds `busy_printers` from it; `_dispatch_holds` adds an in-memory post-dispatch window. ⚠️ **Every print now also holds a queue ROW while it runs** — direct prints take it at dispatch (`queue_batch.claim_printer_for_direct_print`, `status='printing'`, `position=0`), external ones at print start (`mark_queue_printing_for_printer`); the dispatcher owns the release. **Routing is NOT dispatching (auto-queue).** `find_eligible_printer` must never gate on *readiness* — plate-clear gate, drying, stagger are `check_queue`'s questions, asked again at dispatch. **The dispatch guard asks the plan, not the feed (2026-09-30).** Between the dispatcher's preflight and publish one question is asked — `filament_preflight.plan_holds`, by `settle_plan`, `final_guard` and the synchronous `DispatchRoutingGuard.validate` — and only of the slots the plan CHOSE, through the resolver's own `filament_routing.source_fits` (plus `feed_preconditions` / `channel_refusal`): a spool swapped in a slot the job does not use, a new tag on the same filament or a remain update is not a changed plan; `unknown` waits, never passes. **A long walk holds neither the transaction nor the loop (m148).** External-folder scanning lives in `services/library_scan.py`: stat / hash / 3MF parse happen with **no session open** and off the event loop via `to_thread`; writes go in `BATCH_SIZE` chunks, each its own short transaction (sized for *lock time*, not commit cost — WAL + `synchronous=NORMAL` means a commit costs no fsync). Doing it the old way took SQLite's write lock from the first `flush` to the final `commit` with a whole NAS walk in between, and unrelated queries died with `database is locked` naming an innocent victim. ⚠️ **Therefore the request cannot wait for the result** — `POST /library/folders/{id}/scan` answers `202 {job_id}`, never counts; progress rides the socket, the summary is the `library_scan_jobs` row. ⚠️ **Reachability is checked in the worker, not the handler** (`Path.exists()` blocks on a hung mount). ⚠️ **Short transactions cost the rollback that used to make a failed scan harmless** — so `remove_vanished` refuses every deletion when the walk came back empty against a stocked folder (`EMPTY_WALK_GUARD = 1`, `skipped_deletions=True`, reported on screen): an unreachable share is indistinguishable from a folder somebody emptied. ⚠️ **Ending a scan is TWO halves** — the row *and* the socket; `_fail_job` does both, and the event carries `folder_id` or the strip it should clear cannot be found. ⚠️ FK `ON DELETE CASCADE` on the job rows is honoured by PostgreSQL only — this codebase never sets `PRAGMA foreign_keys = ON`.

**Free stock of product parts is a LEDGER with one writer (m162).** `product_part_stock_movements` holds signed movements per product part (`surplus_banked` · `unfiled_print` · `reserved_for_order` · `reservation_released` · `manual`); the balance is Σ delta, never a column. **Only `services/part_stock.py` writes the table** — routes, `on_print_complete`'s `_credit_free_stock` hook and the part/product delete–merge paths call it; readers may live anywhere. **Every door that moves a product's configuration, orders or stock goes through the product gate, and locks in one order (WS-13 E1, 2026-09-29).** Waiting locks are taken in class order, ascending id within a class: `library_files` → `products` (the GATE) → `projects` → `stock_items` → `project_lines` → `product_parts` → `project_procurement`; a door that needs several takes them in that order and never goes back to a lower class. The gate is `services/product_gate.py::product_gate(db, product_ids)`: `FOR NO KEY UPDATE` on PostgreSQL (`take_write_lock` on SQLite), taken FIRST in a clean session, ascending — on its first entry it refuses (`GateOrderError`, in production too, never logged-and-continued) a dirty session, a lower id than one it holds, or a caller already holding a lock of class ≥ 3; re-entry does nothing and issues no SQL; a product this transaction created is skipped. Multi-line doors take positions → lines → parts through `finished_stock.lock_lines_with_parts`; a line door locks the positions first (`lock_line(also_keys=…)` names the configuration it is about to move to) and a set of positions that changed under it is 409 `stock_changed`, never a late lock. Variant and configuration writers never WAIT behind the gate: their footprint is taken `FOR UPDATE NOWAIT` (`lock_nowait`), and SQLSTATE 55P03 — read off `core/database.sqlstate`, never the driver's exception type — answers 409 `{"error": "product_busy"}`. `core/lock_ledger.py` records what the OUTER transaction holds across savepoints (a snapshot at a savepoint's start, kept on RELEASE, restored on ROLLBACK TO; rows the transaction INSERTed are marked by an `after_flush` listener and never lock-contended); its monitor raises on an out-of-order lock under `BAMDUDE_LOCK_ORDER_STRICT=1` (the test conftest sets it) and logs once per key in production. The PostgreSQL scenarios (`tests/integration/lock_protocol_scenarios.py` + `test_postgres_scenarios.py::TestLockProtocol`) stop session A inside its operation on a named barrier and watch session B in `pg_stat_activity` — a test that runs A to completion before B starts cannot see a deadlock. **Finished goods are columns and a ledger with one writer (WS-09, 2026-09-27).** `stock_items` (m191) holds one position per product configuration — `UNIQUE(product_id, config_key)`, the same key as an order line, `AUTOINCREMENT` for its `SK-` code — with `on_hand` / `reserved` / `min_qty` / `location` as COLUMNS: lists, filters, sort, tiles and the sidebar's «below minimum» (`min_qty > 0 AND on_hand − reserved < min_qty`) are SQL over them, and CHECKs keep `0 ≤ reserved ≤ on_hand`. `stock_item_movements` is the history, with its actor. Only `services/finished_stock.py` writes either (`tests/unit/test_finished_stock_has_one_writer.py`): it locks the position row for each read-decide-write — `FOR UPDATE` on PostgreSQL; on SQLite, whose dialect emits none and whose pysqlite opens a transaction only at the first write, `core/database.take_write_lock` takes the write lock with a no-op UPDATE BEFORE the read (two reservations both landed without it; `part_stock.lock_part` does the same for the parts ledger) — and moves the columns and the ledger together — the columns always equal the sum of the movements — and never writes a zero row; the kinds are the closed `MOVEMENT_KINDS` (frontend copy `STOCK_ITEM_KINDS`, labels in both locales). A stocktake takes the COUNTED quantity and records the difference (below the reservation is 409; a lower count needs a note). A position's configuration (`stock_item_choices` / `stock_item_part_counts` / `config_key`) is `line_config`'s, like an order line's: `resolve` applies the same rules, and every product edit that moves line configurations (`add_group_to_lines`, `freeze_binding`, `forget_part`, `repoint_part`) re-keys positions too — 409 when two positions would become one configuration. Assembly is one transaction over both ledgers: the kit's printed parts (through `line_composition`) leave the free shelf by `part_stock.move(reason="assembled", stock_item_id=…)` and the position grows; bought parts are not written off. Both ledgers stamp `created_at` in Python UTC (a server default is local time on a non-UTC PostgreSQL), and `GET /stock/journal` merges them on a `(created_at, book, id)` keyset at full microsecond precision — never truncated (SQLite's `strftime('%f')` rounds where Python truncates, and a page boundary lost rows); legacy parts rows on SQLite (no fraction) are padded to six digits before they are compared. A position is created by a receipt, a count above zero or an assembly, serialised on the product row; a deleted customer is detached from issues in code (`detach_customer`); an API key's writes are recorded against its owner (`core/auth.acting_user`). SQLite runs no FK actions: deleting a product is 409 while anything is on hand or reserved and removes its empty positions in code (`delete_for_product`); deleting a user nulls the actor in both ledgers (`detach_user`). **What an order line takes from stock is decided by ONE function, and lines are added in ONE transaction (WS-10, 2026-09-27).** `services/stock_pick.py::suggest` is the only place that answers "how much of this line comes off the shelves": ready units of THAT configuration's position first (`min(quantity, free)`), then kits of free parts on the rest, the remainder to print; it writes nothing, runs a fixed number of queries for any list (named lines included — they are read together), and with `line_id` counts what the line already holds, and what it already issued on a reactivated order, as its own. `POST /stock/suggest` (the «Add to order» dialog, «Pick from stock» on a line) and the batch's `stock: "auto"` both call it — the frontend never computes a proposal, it only clamps the operator's own numbers to the «of N» of the same answer. `POST /projects/{id}/lines/batch` (`services/line_intake.py::add_lines`) takes `product` / `parts` / `plate` lines in one transaction — a refused line adds nothing, with that line's own sentence and no line number; `POST /projects/{id}/lines` and order creation run the same code with one line. What the shelf gives may be less than asked (it moved since the proposal): the writers reserve `min(asked, free)` under their locks and the answer carries `asked_*` / `got_*` — clamped, never refused; an `auto` row is re-picked at confirmation, so its `asked` equals its `got`, and the dialog compares `got` with what the row SHOWED. **An order's goods are issued through ONE function, and an order completes only fully issued (WS-11, 2026-09-27).** `services/order_fulfilment.py` answers what each line can assemble, receive and issue now (`state`, with the order's `can_assemble` / `can_receive` / `can_issue` totals the banner shows — never summed on the client) and performs a batch (`apply`): the positions its lines hold locked in ascending id, then the lines, then the state read AGAIN; a number above it is a 409 sentence and nothing is written (an issue is physical units — refused, never clamped); per line assemble → receive → write off → issue; at most ONE `stock_issues` row per batch. Receiving is capped by the ORDER's prints, not by a line's share of them: per part, Σ `received × per` never exceeds what the order's prints made (`usable`), and what is left is shared out in line order — `attribute` moves prints between lines when needs change, a line's `received` does not, and a per-line bound alone received one print twice. A line of a product without printed parts is received as its units come. The positions a batch writes — held ones AND each line's own configuration — are locked in ascending id before the lines (`lock_positions_for_lines`), assembly locks the position before the parts, and the status is read again under the locks. The line counters `project_lines.assembled` / `received` / `issued` / `returned` / `written_off` (m191) are written only by `finished_stock` (its guard covers them), a parts line's by `part_stock` in `project_line_part_stock` (own guard); held on the shelf for the order = `from_finished + assembled + received − issued − returned − written_off` = Σ `delta_reserved` of the line's finished movements. What belongs to an order never reaches the free parts balance: `reservation_released`/`assembled`, `made_for_order`/`held_for_order`, `hold_released`/`issued_for_order`, `hold_released`/`written_off_for_order` are zero-sum pairs, and a cancel lifts the hold alone. A write-off (movement `written_off`, a note required — 422 without) is a unit that broke on the shelf: the order needs it made again — its need and its surplus count `quantity + written_off` (a parts line: `per + written_off`), so the plan prints one more and the replacement is not surplus. `stock_issues` has one writer (`services/stock_issues.py`, guard test): a recipient SNAPSHOT (name, phone, delivery method NAME, details), a waybill ≤ 24 characters and a note — the only two things `PATCH /stock-issues/{id}` changes; both ledgers' movements carry `stock_issue_id`; a manual issue off the stock page names its customer (422 without). **Measurement history is written ABOVE the plug drivers, never from a device listener.** `services/measurement_history.py` (driven by `smart_plug_manager._history_loop`) is the only writer of `smart_plug_power_history`; sensors reach `smart_sensor_history` the same way through `services/measurement_buffer.py`. **A switched-off plug reports 0 W, as physics — not as trust in the device.** `zigbee/driver.py::get_energy` returns `power: 0.0` whenever the known state is `OFF`, whatever the reading cache holds; an unknown state is NOT treated as off. Cheap plugs keep reporting the last measured watts/amps after the relay opens (S60ZBTPF pre-2.0.3 firmware did exactly that, and BamDude showed 33 W for an empty socket). The upstream quirk fixes only transitions it witnesses, so it cannot cover a restart. `total` is never zero-filled — a fabricated zero would be differenced as real consumption. **Zigbee quirks need two conditions, both silent when broken:** `ControllerApplication.new()` must get `device_resolver=` (without it zigpy applies NO quirks at all), and attribute values must come from `cluster.get(attr)`, never from what `read_attributes` returned (that is the raw pre-quirk value, and zigpy suppresses the update event for the attribute being read). Verify with `GET /zigbee/devices/{ieee}/attributes` — `device_class` must be `CustomZigpyDevice`, and raw vs cached diverge exactly where a quirk acted. **Reports arrive on `on_event`, never on `add_listener` alone** — zigpy 2.x delivers a reported attribute inside `_suppress_attribute_update_event`, so the legacy channel hears nothing at all; `reporting.py::_subscribe_cluster` is the single place both channels are wired, and a listener needs `__call__(event)` as well as `attribute_updated`. A stub that only has `add_listener` will confirm whatever wrong model you hold (it did, for 300+ green tests). The 30–45 s poll (`zigbee/poller.py`) is the **floor**, not the mechanism — measured 35 value changes in 3 min from reports vs ~5 from polling — and it stays because ZHA polls `ElectricalMeasurement` by default too (exempting 4 allowlisted models), while for `Metering` the rule is inverted (no poll except 3 known-bad models). **Reporting bounds are per cluster, from ZHA, not one shared triple** (`_POLLED_CLUSTERS` carries a `_ReportingBounds` per row, pinned by `test_the_bounds_asked_of_each_cluster_are_zhas`): OnOff `0/900/1` (a relay cannot chatter by itself; a floor only delays the answer to our own command), Metering summation `30/900/1` (it only ever grows, so "changed by 1" holds continuously — at 5 s that is a message every few seconds all print long), ActivePower `5/900/1`. `min_interval` is the floor between two **device reports**, not a poll interval. Battery sensors are never polled: `power_class` reads `node_desc.is_receiver_on_when_idle`, **not** `getattr(flags, "RxOnWhenIdle")`, which returns the always-truthy IntFlag member.

**Sensor reporting has three outcomes, not two.** `unanswered` (a sleeper that never woke — the usual case) ≠ `refused` (an explicit non-SUCCESS from the device) ≠ `ok`. Only a complete apply records the desired state; anything less is retried at the next contact, or one badly timed moment leaves a measurement unconfigured until re-pairing. Defaults live in `zigbee/measurements.py` (pinned by `test_the_defaults_are_the_agreed_ones`), taken from ZHA. `reportable_change` conversion branches on `raw_is_integer`: integer attributes floor at 1, floats must NOT — 1 ppm of CO2 is `0.000001` raw, and flooring it to 1 asks for a report every million ppm, i.e. silence forever.

Everything that reasons about the FIRMWARE — client-side backup-group reconstruction (`computeBackupGroups`) and the PrintModal remain-pool key (`groupTraysForBackup`) — deliberately reads the LIVE/advertised fields. ⚠️ Routing's two STRICT checks are the exception (owner, 2026-09-30): a forced colour and a strict profile compare with what the operator DECLARED (`FeedSource.declared_color` / `declared_variant`, read through `rule_color` / `rule_variant`; frontend `amsHelpers.declaredColor` / `declaredTrayInfoIdx` over `advertisedColor` / `advertisedTrayInfoIdx`; the offline wake step through the printer's canonical colour), and so does colour ranking — a backup group built from leftovers outranks the job's «exact» box. Base material, archive colour, attribution, `filament_low` and preheat stay on the spool. Applied overlay entries enter the feed snapshot's `revision` (sorted), so the latch key and the auto-queue placement check see them. RFID slots (valid tag on the live tray OR the spool) and external slots are never projected; the two hardware-decided knobs (`GENERIC_BASE_MATERIALS`, `GENERIC_MODE_KPROFILE`) live only in the policy module and change only with a capture on P1S+AMS and X2D+AMS 2 Pro. Bulk re-advertise (`POST /printers/{id}/ams-policies/backup-compatibility/apply`) previews with `dry_run`, refuses while printing (409) and without printer state (400), and its `revert` action re-publishes the actual plan for a slot the policy no longer projects — the same button rolls back after the policy is switched off. `filam_bak` is the only proof a group formed; an `ams_filament_setting` ACK proves acceptance only.

**A slot "matches its spool" when it shows the type WE wrote, not the material column (upstream #2902, 2026-09-24).** A non-RFID assignment's fingerprint is the slot BEFORE our `ams_filament_setting` (`assign_spool` snapshots it first), so the first AMS push after every such assign differs from it and the link survives only through `on_ams_change`'s "tray matches the spool" check. That check asks `routes/inventory.tray_types_written_for` — the slot plan's `tray_type` (family type, or the generic family's when the spool has none) plus the material — through `spool_slot_plan`, the SAME computation `apply_spool_to_slot_via_mqtt` publishes from. Never compare with `spool.material` alone: `PLA-AERO` ≠ `PLA`, and a family-less "PLA Matte" spool is written as `PLA`. Vault: `40-invariants/inv-slot-matches-what-we-wrote.md`.

**A spool without a family keeps ITS type on the slot; only the profile is borrowed (upstream #2902 / 88e8ca81, 2026-09-25).** When `build_slot_assignment` has no family (a Spoolman spool without a linked K-profile, a quick-added or legacy one — and the P*→system degrade on a printer without user presets), `slot_assignment._stand_in` asks `utils/filament_catalog.family_for_material`: a family whose name the material IS, else the family of EXACTLY the type the name states (`material_type`: words joined with a hyphen, the longest join that is a catalogue type, routing equivalences applied — "PLA Aero" → PLA-AERO → Bambu PLA Aero; PLA+ / "PLA Matte" → Generic PLA), Generic first, else the catalogue's own (Bambu Lab first). A name that is no known type ("ASA-GF") borrows the BASE generic's profile and keeps the spool's type as given. ⚠️ Never configure a slot from `generic_family_for_material`: it cuts the name at the first hyphen/space and the old code took that generic's TYPE too, so PLA-AERO went out as PLA — and routing compares nothing but the slot's `tray_type` under the default base-material matching, and AMS Backup groups by the profile. `resolve_raw`'s material-name fallback answers through the same function (it is what a spool save persists as `filament_family_id`). Authoring and the backup-compatibility policy keep `generic_family_for_material` — they ask for a base to inherit from, a different question. Vault: `40-invariants/inv-a-spool-without-a-profile-keeps-its-type.md`.

**The in-app inbox is a channel, not a provider row (m176).** `services/notification_inbox.py::INBOX_CHANNEL` rides the list `NotificationService._get_providers_for_event` returns, so the 32 `if not providers: return` guards stay truthful and the inbox fills on a farm with no provider at all; `_send_to_providers` delivers it FIRST and skips the provider bookkeeping — it never writes `notification_logs` (a journal of external deliveries, `provider_id NOT NULL`), never enters the digest and ignores quiet hours. Fan-out on write: one `user_notifications` row per subscribed active user (`users.inbox_events`, NULL = every warning/error of `services/notification_events.py::EVENT_CATALOG`, the ONE catalog of severity + group; a test pins it to `PROVIDER_EVENT_DEFAULTS`, both template files and the Telegram vocabulary). `IN_APP_ONLY_EVENTS` is empty and stays disjoint from every `on_*` flag — an event listed there reaches the inbox only through `notify_in_app`. `deliver` commits the caller's session like `_log_notification` does and never opens a second one. Permission `notifications:inbox` is a person's, seeded to all three default groups and denied to API keys. ⚠️ **The provider form and the provider card render their event toggles from `GET /notifications/events`, never from a list of their own** — three hand-kept frontend lists had drifted to 18 of the 34 flags, six of which default to ON, so a new provider sent events nobody had been shown; an unknown flag renders under a derived label rather than disappearing (`components/ProviderEventToggles.tsx` + `providerEvents.ts`; the route is declared above `GET /{provider_id}` or `events` parses as an id). SQLite ignores the FK cascade: `delete_user` removes the rows. Vault: `40-invariants/inv-inbox-is-a-channel-not-a-provider.md`, `60-specs/notification-center-spec.md`.

**The K-profile table is filed per nozzle diameter; the cache prunes only what a held table dropped (upstream #2854/#3044, 2026-09-24).** An `extrusion_cali_get` reply is the complete table for ONE diameter, and the printer answers whoever asks — BambuStudio on the same topic, the git backup's 0.2–0.8 probe, the spool dialog per fitted nozzle. `BambuMQTTClient._store_kprofiles` files each reply under its diameter and `state.kprofiles` is the union (a `get_kprofiles` waiter still receives only its own reply; the history view is filed the same way). ⚠️ `cali_idx` is numbered per nozzle AND per hotend, so nothing matches a live profile on the index or the name alone: the card's K goes through `utils/kprofile_lookup.build_slot_k_resolver`, shared by the REST and WebSocket shapers (the slot's own extruder first; an index-only fallback only when the candidates agree, fitted diameters as tie-break; an AMS the extruder map does not name is UNKNOWN, not extruder 0 — a deliberate divergence from upstream), and the bind / PA-tab link / note / audit lookups filter on `nozzle_diameter` + `extruder_id`. A spool holds ONE PA profile per printer / extruder / nozzle diameter / flow type — BambuStudio's identity for a PA profile — so the PA tab keys its selection through `spool-form/utils.ts::profileSelectionKey` (never a hand-built `printer:cali_idx:extruder` string), and the bind prefers the link of the flow type it is given. ⚠️ **Every binder asks `utils/slot_nozzle.slot_nozzle(state, ams_id, tray_id)` for the slot's extruder, diameter and flow** (`state.nozzles` is indexed by extruder id, 0 = right/main) — never `nozzles[0]`, never `getattr(state, "nozzle_volume_type", …)` (the state has no such field; that constant made every High Flow calibration unreachable, and `test_kprofile_bind_reads_the_slots_nozzle.py` scans for it). A printer that reports no flow class (X1C/P1/A1 name the nozzle by material) binds as Standard, which is how the sync stores its undeclared rows; Configure Slot filters by the fitted flow only when both the printer and the profile declare one (`resolveSlotNozzleFlow`). ⚠️ `sync_printer_kprofiles_to_cache` hard-prunes only rows whose diameter has a non-empty table in `live` — a diameter never read is unknown, and an empty answer stays ambiguous and prunes nothing. The fitted diameters are read once per connection when a push first names one (`on_kprofile_tables_due` → `printer_manager._prime_kprofile_tables`); the blind 0.4 prime on connect stays. Vault: `40-invariants/inv-kprofile-table-per-nozzle.md`.

**A command's acknowledgement is not the printer's status (upstream #3040, 2026-09-24).** The printer echoes a command's fields back on the report topic in the same `print` envelope as a status push, and every such frame runs through `_process_message` / `_update_state`. A field a command can carry as a REQUEST — the per-job `cfg` storage bit of `project_file` (`utils/timelapse.task_cfg`, which we send exactly as BambuStudio does, "4"/"0") and its `timelapse` — must be read only from a status frame: `bambu_mqtt.is_printer_status_frame` (`command` absent or `push_status`). Every `cfg` decoder (AMS settings bits, print options, print-option support) and the timelapse state go through it; read from the ack, our own "0" switched them all OFF after each dispatch and advertised "store sent files" on P1/A1, which send no `cfg` of their own. ⚠️ Not a blanket "ignore acks": the named `print_option` echoes are read on purpose as the confirmation of a set, and `_route_ack` / the dispatch capture need the ack. Vault: `40-invariants/inv-command-ack-is-not-status.md`.

**A 3D-model site is a `ModelProvider`, and the routes reach it only through one (upstream #2845, 2026-09-25).** `services/model_providers/` holds the interface (`base.py`: a `ModelProvider` descriptor — identity, `host_patterns`, `default_folder_name`, `view_permission` / `import_permission`, `parse_url` / `canonical_url` / `source_url_filter`, the SSRF allowlists `thumbnail_hosts` / `download_hosts` — plus a per-request `ProviderService`: `get_status` / `resolve` / `get_download` / `download` / `fetch_thumbnail` / `close`) and the `registry`; MakerWorld is the first implementation (`makerworld/`, registered on package import). The `/makerworld/*` routes pick the provider through `registry.find_for_url` (resolve) or `registry.get(source_type)` (import — an unknown one is a 400 BEFORE the default folder is created), build ONE service per request via `provider.build_service(db=, user=, api_key_owner=)` and close it once, after the meta row and covers. ⚠️ Every endpoint keeps its own `RequirePermission` (MakerWorld's, read off the descriptor); `routes/makerworld._authorize_for_provider` checks a provider's permission ON TOP when it differs — never upstream's "authentication only" route gate. ⚠️ The Bambu Cloud credential has ONE seam, `services/bambu_cloud_credentials.py` (`get_stored_token`, `is_cloud_token_invalid`, `mark_cloud_token_invalid`, …): services import it, never `api/routes/cloud.py` (`test_services_take_credentials_from_the_seam.py`); refresh + sign-in stay in the route. ⚠️ `makerworld/http.py` sends our honest versioned User-Agent, never upstream's. The old `services/makerworld.py` / `makerworld_meta.py` are gone — m056's import lines were repointed rather than keeping shims (owner's call; `test_makerworld_has_one_home.py`). The meta table (m056), the import history and the page stay MakerWorld's; generalise them when a second site arrives. Vault: `40-invariants/inv-a-model-site-is-a-provider.md`.

**Spoolman no-3MF tracking.** For "Untitled" prints with no `.gcode.3mf`, `spoolman_tracking.py` snapshots each AMS slot's `remain%` + `tray_uuid` at start (`_snapshot_tray_remain`) and writes consumed grams from the drop × curated reference weight — only for slots the 3MF didn't cover, skipping mid-print-swapped slots. ## Code Style

- **Python** Ruff (line 120, double quotes, py312); B008 ignored for FastAPI `Depends()`. See `pyproject.toml`.
- **TS** ESLint flat config, strict mode.
- **Commits** Conventional (`feat`, `fix`, `docs`, `test`, `refactor`, `chore`).
- **Branches** `feature/`, `fix/`, `docs/`, `refactor/`, `test/`.
- **PRs** target `dev`, not `main`.
- **CHANGELOG** user-facing only — no `temp/*` or audit MD refs.

## Branching & Release

- `main` — production; `kainpl/bamdude:latest` + `ghcr.io/kainpl/bamdude:latest` track it.
- `dev` — active dev; CI on push+PR. A push to `dev` publishes no image (the `Docker Build` CI job only builds and probes one); `:dev` moves with every pre-release tag.
- `feature/*` — short-lived; long-running upstream-port branches track `dev` via periodic merges.
- **Channels**:
  - **Stable** `vX.Y.Z` on main → `:latest` + `:X.Y.Z`. `gh release create` after dev→main FF. **Docker publishes itself** — pushing a `v*` tag fires `docker-publish-tag.yml` (GHCR + Docker Hub, both arches), `windows-installer.yml` and `publish-code-graph.yml`; never also run the script.
  - **Beta** `vX.Y.ZbN` on dev → `:X.Y.ZbN` + `:dev` (no `:latest`).
  - **`:dev`** = the latest beta, moved by that tag (since 2026-08-18); `docker-publish-dev.yml` is a manual `workflow_dispatch` for the raw `dev` head only.
- **The CI gate is the run on `dev`, never the one on `main`.** `ci.yml` opens with `check-duplicate` (`fkirc/skip-duplicate-actions`) and every job hangs on `if: needs.check-duplicate.outputs.should_skip != 'true'`. A FF `dev` → `main` is the *same SHA on another ref*, so main's run skips every job and reports ✓ in ~10s having tested nothing. Order: push `dev` → `gh run watch --exit-status` on dev → FF `main` → tag. Skipping this shipped 0.5.1.2, whose dev run was red while main showed green.
- **Naming — one format, no exceptions.** Tag `v<version>`; release title `BamDude v<version>`, plus ` (pre-release)` when prerelease. No subtitles in the title — the body and CHANGELOG say what's in it. Drift check: `gh release list --limit 100 --json tagName,name,isPrerelease --jq '.[] | select(.name != ("BamDude " + .tagName + (if .isPrerelease then " (pre-release)" else "" end)))'` must print nothing. Titles are cosmetic — `gh release edit <tag> --title` touches no tag, image or asset, so fix in place, never re-release.
- **Tag immutability** — never force-push. Ship `X.Y.ZbN+1` or `X.Y.Z.1`.

## Adding Features

- **API endpoint** — schema in `schemas/` + route in `api/routes/` + register in `main.py` + permission if needed.
- **DB model** — model file + `database.py` import + migration + schema + route.
- **Column** — model file (fresh installs) + `add_column()` in latest migration (existing DBs) + Pydantic schemas + frontend types.
- **Telegram handler** — handler file + register in `telegram_bot.py` + i18n in BOTH `telegram_ui_{en,uk}.json`.
- **Notification trigger** — `notification_service.py` + BOTH `notification_templates_{en,uk}.json`.
- **Maintenance type** — `DEFAULT_MAINTENANCE_TYPES` in `routes/maintenance.py` with `type_code` + BOTH `maintenance_types_{en,uk}.json`. Model-specific → `_ROD_TYPE_REQUIREMENTS`.
- **Public frontend feature** — `npm run build` in verify; `static/` ships same commit.
- **Any of the above** — update the matching vault note in the same batch (see *Knowledge base*, rule 4). New subsystem → new note per `00-index/_design.md`; new invariant → `40-invariants/`. This is part of "done", not a follow-up.

## Upstream (Bambuddy)

BamDude is a hard fork of Bambuddy. Upstream releases are **adapted, not
merged**: the maintainer keeps a per-release audit in which every upstream
change is marked applied or rejected with a reason. When porting an upstream
change, first audit our own state around it — the two-tier queue (per-printer +
AutoQueue distributor), the dispatch claim per printer, the archive
chain-of-custody — and adapt the change onto that, never re-implement
upstream's flat model beside it.

## Bambu Studio reference

Bambu Studio is the protocol authority for Printer Settings, AMS Settings,
Filament Calibration, the `print.command="*"` dispatch mappings, gcode stage
strings and the canned calibration assets in `backend/app/data/calib_assets/`.
We mirror **protocol and assets only** — BS code is never merged. The
maintainer re-syncs the mirrored areas against each BS release.

### Mirrored printer configs (`backend/app/data/printers/`)

Parsed-JSON-equivalent copies of the complete BS `resources/printers/*.json` catalog (one per model plus `filaments_blacklist.json`) — the data-driven source of truth for model descriptions, compatibility, and **per-model device capabilities** (`support_*_calibration`, `support_bed_leveling`, chamber, camera, …). Read by `utils/printer_configs.py` (`load_printer_config` + `device_calibration_availability` + the hybrid `resolve_device_calibrations`, which overrides the JSON base with the printer's live `support_*` MQTT flags) and `utils/model_compatibility.py`. **Re-sync from the chosen BS Git ref, not the reference checkout's possibly older working tree**; compare complete file sets and parsed JSON, then review all changed fields — full protocol in that folder's `README.md` (also records the source BS tag). Files are named by internal code (`N6.json`=X2D); the loader keys off each JSON's own `display_name`/`model_id`, **not** `PRINTER_MODEL_ID_MAP` (corrected in 0.4.7 to `C11`=P1P, `C12`=P1S per BS, with `BL-P001`=X1C/`BL-P002`=X1 added). New models must be recognized by backend and frontend name maps without guessing unsupported capabilities. Device calibrations run via one MQTT command `{"print":{"command":"calibration","option":<bitmask>}}` — bits: 0=lidar(xcam) 1=bed_leveling 2=vibration 3=motor_noise 4=nozzle_offset 5=high_temp_bed 6=clump_pos.
