# Invariants: Notifications and Telegram

Full text of the rules that [`CLAUDE.md`](../../../CLAUDE.md) keeps in short form, with the reasons and the history behind them. `Vault:` pointers name notes in the maintainer's private knowledge base; everything a contributor needs is here.

## Telegram dispatch authority is the chat (m045+)

`NotificationProvider` rows of `provider_type='telegram'` keep only `enabled` + `daily_digest_*` + token + name (+ `printer_id`). The 24 `on_*` flags + `quiet_hours_*` are forced True/False by m045 + `_coerce_telegram_provider_fields`. Per-chat `TelegramChat.{notify_events, quiet_hours_*, daily_digest}` is sole authority. **Never reintroduce a provider-level event toggle for telegram.**

## A telegram provider IS a bot, and one polling session holds them all (m180)

Every ENABLED telegram row is its own bot: one `Dispatcher`, one `_run_polling(dispatcher, bots)` task, `start_polling(*bots)` (aiogram runs a long-poll task per bot inside it and hands each handler `event.bot`). **Never a second `Dispatcher`** — the handler routers are module singletons aiogram attaches to one — and never a hand-rolled `getUpdates` loop. The registry is `telegram_bot._bots` (provider id → `Bot`) + `_bot_ids` (Telegram account id → provider id, from `get_me`); readers are `get_bot(provider_id)`, `send_message(provider_id, …)`, `send_photo(provider_id, …)`, `provider_id_for_bot`, `running_bot_provider_ids`. A token whose `get_me()` fails costs only its own provider a bot (the error goes to that row's `last_error`); the rest start. **A bot token belongs to ONE telegram row** — a 409 at create/update, m180's `dedupe_tokens` for what was already stored, and a start-time backstop (oldest polls) — because Telegram serves one `getUpdates` per token. The lifecycle stays behind one `asyncio.Lock` (`start`/`stop`/`restart` end to end, `restart` across both halves, the registry detached before the first await, bounded shutdown); a provider save restarts the session only when `current_bot_providers()` — every enabled row as `(id, token)`, `ORDER BY id` (unordered is heap order on PostgreSQL, which an UPDATE moves) — answers differently. **A chat is the PAIR `(provider_id, chat_id)`**: Telegram's private chat id is the person's user id, identical in every bot, so the same person in a second bot is a second row with its own role and scope. `telegram_chats.provider_id` is NOT NULL; two writers only — the middleware at registration (from `provider_id_for_bot(event.bot.id)`, never "the first telegram provider") and `POST /telegram/chats` (the provider named, else the only one, else 400 / 409). There is deliberately NO re-bind on contact. Auto-registration's "first setup" is per bot; `telegram_registration_open` stays global. Every fan-out to "a provider's chats" filters on the column (`_send_telegram_to_chats`, `_send_telegram_digest_to_chats`, `_has_telegram_digest_subscribers`, `_send_telegram` all take `provider_id`); per-chat module caches key on `(bot account id, chat id)`. Deleting a telegram provider removes its chats **in code** (SQLite runs no FK actions; the CASCADE is the PostgreSQL backstop). Vault: `40-invariants/inv-telegram-chat-belongs-to-its-bot.md`, `40-invariants/inv-one-telegram-poller-per-process.md`, `60-specs/telegram-multi-bot-spec-plan.md`.

## The in-app inbox is a channel, not a provider row (m176)

`services/notification_inbox.py::INBOX_CHANNEL` rides the list `NotificationService._get_providers_for_event` returns, so the 32 `if not providers: return` guards stay truthful and the inbox fills on a farm with no provider at all; `_send_to_providers` delivers it FIRST and skips the provider bookkeeping — it never writes `notification_logs` (a journal of external deliveries, `provider_id NOT NULL`), never enters the digest and ignores quiet hours. Fan-out on write: one `user_notifications` row per subscribed active user (`users.inbox_events`, NULL = every warning/error of `services/notification_events.py::EVENT_CATALOG`, the ONE catalog of severity + group; a test pins it to `PROVIDER_EVENT_DEFAULTS`, both template files and the Telegram vocabulary). `IN_APP_ONLY_EVENTS` stays disjoint from every `on_*` flag; internal retirement and Git-backup admission notices use an explicit caller-owned staging transaction with their durable episode marker and unique recipient key. Postcommit dispatch uses scalar payloads + immutable recipient identities, never SQL or provider delivery. `deliver` retains its ordinary callers' commit behavior like `_log_notification` and never opens a second session. Internal startup delivery begins after technical admission; failure leaves a bounded retry, never closed sign-in. Permission `notifications:inbox` is a person's, seeded to all three default groups and denied to API keys. One event carries its sender's level instead of the catalog's: an external app's message (`external_app_message`, `POST /notifications/external-message`, owner 2026-11-21) — its inbox rows take the requested severity (`deliver(severity=…)`), and its SENDER (key · owner) is added by code, never by the editable template: inbox `extra_data.sender`, the other channels a last line. Only an API key with `can_send_notifications` (m252) whose owner is active and holds `notifications:update` may send; a browser session is refused. ⚠️ **The provider form and the provider card render their event toggles from `GET /notifications/events`, never from a list of their own** — three hand-kept frontend lists had drifted to 18 of the 34 flags, six of which default to ON, so a new provider sent events nobody had been shown; an unknown flag renders under a derived label rather than disappearing (`components/ProviderEventToggles.tsx` + `providerEvents.ts`; the route is declared above `GET /{provider_id}` or `events` parses as an id). SQLite ignores the FK cascade: `delete_user` removes the rows. Vault: `40-invariants/inv-inbox-is-a-channel-not-a-provider.md`, `60-specs/notification-center-spec.md`.
