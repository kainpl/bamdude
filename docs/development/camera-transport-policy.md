# External camera transport policy

Camera connections, snapshot decoding and FFmpeg remain owned by the supervised camera worker. The main server retains authorization, relay and the existing fan-out buffer. This policy does not add a second capture path or change who can read, replace or test a stored camera URL.

## HTTP destinations and redirects

Initial URLs and every redirect target are checked before the corresponding request. Cloud metadata spellings, link-local and unspecified addresses, ambiguous numeric IP spellings, malformed authorities and ports, control characters and backslash parser ambiguities are refused. Private LAN addresses, IPv6 ULA and loopback are intentional camera destinations, including local go2rtc. Use an ASCII DNS name or a supported IP literal; Unicode hostnames and IPv6 zone identifiers are refused.

Raw `@` characters in credentials are supported: the host always follows the last `@`. Raw ASCII spaces in credentials, path and query remain supported; scheme, host and port must contain no spaces. Other whitespace and control characters remain refused. Known metadata IPv4 addresses embedded in the NAT64 well-known prefix or 6to4 are refused too; arbitrary translation prefixes and DNS routing remain outside this spelling policy.

HTTP follows at most three redirects under one header deadline. A finite capture also has one deadline spanning the redirects and body; live MJPEG instead retains its read-stall timeout after the headers. Relative redirects are supported. Loops, malformed locations and HTTPS-to-HTTP downgrades are refused. Basic credentials and cookies can continue on the same origin (scheme, host and effective port). The first origin change permanently switches that request chain to an anonymous session, including if it later returns to the original origin. Userinfo supplied by a redirect is ignored. An installation that previously relied on credentials crossing origins should configure the final camera endpoint directly.

This is a URL spelling policy. It does not pin DNS answers to the connected socket and does not prevent DNS rebinding. Do not treat configured camera endpoints as unrestricted untrusted URLs.

## Snapshot bodies and decoding

HTTP snapshot input and JPEG output are each limited to 10 MiB. Image dimensions are limited to 8192 on either edge and 16 million pixels. Supported still formats are JPEG, PNG, WebP and BMP; PNG/WebP/BMP become JPEG in the worker after actual still-image decoding. Explicit HTML, SVG, JSON and other unsupported MIME types are rejected; missing or octet-stream MIME still needs supported magic and the format's image checks. HTTP content compression is refused before reading the body to avoid automatic expansion. Unsupported bodies and rejected images yield no frame, with no raw-body fallback. GIF snapshots and JPEG with trailing bytes after terminal EOI, including padding, are no longer published.

These are capture/parser ceilings, not a promise that every image below them is published. The existing live registry retains its stricter 2 MiB frame limit; the worker media channel retains its 10 MiB limit. Neither publication limit is raised by this work.

JPEG has a bounded fast path without Pillow or a native decoder: magic, terminal EOI, segment lengths, dimensions, component framing and the first scan header are checked, then original bytes are preserved. Baseline, extended sequential and progressive DCT frame headers are supported, with grayscale, RGB and CMYK components. Metadata payloads are skipped by length without copying, with at most 256 header markers before the first scan. Missing EOI, trailing data and malformed checked headers are refused. This path does not validate entropy/MCUs, later progressive scan headers or complete JPEG syntax, and does not prove that every decoder can decode the pixels; damaged entropy with framed headers and EOI can pass. WebP dimensions are checked from its fixed headers before native canvas allocation; PNG/WebP/BMP still require real decoding and a single frame.

At most four application snapshot body/decode consumers and two native decoder futures are admitted per worker. Body admission happens after validated response headers, so a camera that never connects or sends headers cannot occupy shared image capacity. FIFO waiting, connect, redirects, headers, body reads and decoding share the original capture deadline; native admission happens while the caller still holds its body slot. Waiting adds no full application body buffers or queued native executor jobs. JPEG needs no native slot. PNG/WebP/BMP cameras share the two converters, so concurrent conversion can reduce their frame rate. A capacity deadline yields no frame, and cancellation removes the caller's waiting ticket.

aiohttp can prefetch before application admission. Snapshot readers use a 64 KiB low-water and 128 KiB high-water setting, retained across anonymous cross-origin redirects. Already received transport/parser data can overshoot the high-water setting; this is not a hard per-response byte ceiling or a global socket/memory limit. Four responses that send headers but then stall in their bodies can still occupy body capacity until their deadlines.

Repeated snapshot failures are aggregated per category across cameras, at most once per minute. Reports include an event count and a representative configured host (with port), rather than every affected camera. URL userinfo, path, query and exception text are omitted; the host follows the existing destination-metadata visibility policy and may itself contain opaque labels.

Caller timeout or cancellation stops waiting for a native codec, but its decoder slot remains occupied until the codec really finishes. Native threads cannot be forcibly cancelled. Two wedged decoders can exhaust conversion capacity; other operations may then wait out their budgets. A healthy worker heartbeat does not automatically detect or restart them. Explicit termination/recovery of the whole worker generation is the hard stop boundary. These limits bound admission and image size; they are not a hard per-image CPU-time guarantee or a total process memory quota.

## MJPEG, RTSP and cleanup

Live external MJPEG/RTSP rejects a frame over 10 MiB, including a started frame that never receives EOI. One-shot RTSP reads bounded stdout while the existing capped stderr drainer runs concurrently. Process termination/reaping, stdout-reader handoff and TLS-proxy cleanup remain with `CameraAttempt`, including early rejection and cancellation. The existing finite MJPEG warm-up/fallback behavior remains unchanged apart from the shared total deadline.

RTSP redirects happen inside FFmpeg. Initial URL validation, protocol restriction and reactive stderr handling do not prove that a same-protocol redirect cannot contact another destination, including metadata. This work does not supply RTSP pre-connect confinement. Validation uses synthetic images, mocked processes and loopback HTTP/TLS endpoints; it does not establish behavior on a physical camera or printer.
