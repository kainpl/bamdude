# Invariants: Downloads, printer files and video

Full text of the rules that [`CLAUDE.md`](../../../CLAUDE.md) keeps in short form, with the reasons and the history behind them. `Vault:` pointers name notes in the maintainer's private knowledge base; everything a contributor needs is here.

## A download is a job that owns its transfer, its scratch and its caller's standing (G10 D)

`services/media_downloads.py` prepares every download of a printer's files or an archive's videos on the data volume (`DATA_DIR/media-downloads/<job>/`, marked, never the system temp, outside backups) — the two older one-request endpoints included, through a hidden job; nothing on that path calls `read_bytes` or builds a ZIP in memory, and the frontend never reads a download into a Blob (`utils/nativeDownload.ts`). A job is immutable after creation: caller, scope (one printer or one archive), selection and the transport built from the printer row as it was — a later change of address or access code never moves it. Admission is one synchronous step: the place in the queue is taken in the step that counted the places, BEFORE the first disk call, and given back on every way out (a refusal, a cancelled request, a restore — which waits for an admission in flight); each free slot is spoken for ONCE, by the queued jobs in admission order — a slot another account's job is about to take is nobody else's room — and the slots are then GIVEN in that very order (`_its_turn`: only the earliest admitted job that still waits may take a free slot; no semaphore, which is first-come only among tasks that have already reached it, i.e. after the disk step), so a later job never overtakes an earlier admission and what waits behind is exactly what the global and the per-user bounds count; those count the ACCOUNT, hidden one-request jobs included, and the 45-minute lifetime runs from creation, waiting included. While it prepares it holds a live-authority handle (`live_authority`, the coordinator's lease) on the caller's credential, the scope's permissions and the resource; a retired handle — revoked session or key, lost permission, deleted printer, unreadable database, restore — stops the job and nothing prepared is handed out; that is bounded detection after a commit, not a fence before one. Fatal and per-file outcomes differ: byte budget (of bytes TAKEN from the source — a file that broke off is charged what it received), disk reserve (shared with what other jobs were promised; a scratch that cannot be written is the job's failure, never one file's — the FTP and tunnel transports tell THIS server's disk (`insufficient_storage`, reason `local_*`) from the printer's socket, both of which raise `OSError`; a buffered file flushes again when it is closed, and that close is where a full disk is often first heard of, so a close of the staging file that fails is this disk's refusal WHATEVER failed first — FTP's `closing_staging`, the tunnel's `_discard` result — and it outranks a source failure of the same file (reason `local_<error>_after_<first>`): a proven disk failure ends the job, a source failure alone costs one file; only a cancel is never replaced), lost authority, time limit and restore end the whole job and are never worked around by a partial result; a file the printer would not give is recorded, three unavailable in a row stop the attempts, and zero successes is a failure, never an empty archive. A partial result is handed out only after an explicit confirmation. Cancelling asks the transfer to stop and the job reads `cancelled` only after its worker has ended and its scratch is gone — the transports' `join_on_cancel` holds the cancelled caller until then; a task that has not taken its first step is never cancelled (it would run no `finally`): it starts, sees the stop flag and ends the job itself; closing a dialog is never a cancel. The result leaves by two doors, both in `live_media.MEDIA_ROUTES` behind the final delivery gate, both always the whole file (`WholeFileResponse`: `Range` / `If-Range` removed before Starlette sees them, `Accept-Ranges: none`): a one-time grant for a browser session (`TokenType.MEDIA_DOWNLOAD`, stored as SHA-256 and looked up by hash — never through `resolve_ephemeral_authority`; spent by an atomic delete; two minutes to START; bound to the job and the runtime generation; the body is sent under the captured parent session, not the spent secret; an API key is refused at mint) and a header door for API keys. HEAD on the grant URL is 405 and spends nothing; a refusal there before the headers is `download-failed.txt`, never JSON under the archive's name; the grant is masked on EVERY log output — `logging_filters.mask_download_grants` inside `redact_log_credentials` (our formatter, every handler), in the slow-request line itself, and `DownloadGrantFilter` on the `uvicorn.access` logger, installed with or without a log file. A read is promised by a `ReaderLease` and confirmed BEFORE the headers (`start()`: the promise still runs, the runtime is open, the job still shows the result); a promise that ran out cannot be started. A job is found only by the very credential that made it (`same_credential`: this session, this key), in its own scope — another user's, another session's of the same account, another key's and a missing one are the same 404. ⚠️ A route gate knows only its own path, so EVERY door of a job puts the job's own requirements (`JobScope.descriptor`: permissions, the printer and its identity, the archive and its incarnation) on the request's current credential (`_job_requirements`): status, list, cancel and mint prove them through the coordinator (`_prove_job`; its 401 for a target that took the id is answered 404 — a JSON 401 signs the browser out; the list leaves a job out only on a proven 403 / 404 and passes a 503 on with its `Retry-After`, because an empty list would say a download had vanished), both artifact doors send the body under them (`_bind_job`), and a header door refuses a request that also carries `?token=`. An archive's attached video follows the archive's ownership rule alone (no printer right, no printer, `resource_printer_scope=False`); reading its printer needs `printers:files` and a remote descriptor whose `printer_id` is the archive's own, so the centralized key gate refuses a key without that printer. The chooser (`GET /archives/{id}/media-sources`) answers its three lists separately and never calls an unanswered printer an empty list, nor a card the printer has not reported (`sdcard_state_seen`) a missing one. The local video is the one the archive SHOWS — its pointer, read through the seam's `primary_token`, with or without a registry row (a video from before the registry has none); the chooser writes nothing and brings no stale row back, its `asset` id names that version, and the copy proves which file it opened after the queue (`file_identity` of the descriptor, `still_shown` before and after) or leaves the file out as `replaced`. A file's time is compared only when it is `exact`, or with the operator's own offset and then marked assumed — an FTP wall clock is never taken for UTC, a `date_only` time can only rule a file out, nothing is preselected, and no offset reaches an automatic attach. Jobs live in memory: startup removes marked job directories only (foreign entries and links are never entered) and purges every grant; `quiesce` closes admission, waits for admissions in flight, stops every job, proves the workers ended, waits for readers that started and removes every directory. A directory has ONE removal (`_removal`: a task of the runtime, begun once and shared by the janitor, a discard and the drain, awaited shielded) — so a drain never starts a second removal beside the janitor's nor answers over it; it answers at its one deadline, with nothing added, a removal already begun goes on under the runtime, and one still running or one that failed keeps its job as a debt and the restore is refused — the janitor too forgets a job only together with its directory; only lifespan startup reopens. Shift-click ranges run over the list as shown, and a selection is pruned only by a complete, current listing. Vault: `40-invariants/inv-download-is-an-owned-job.md`.

## A file on the printer is deleted only through the file guard (G10 B)

`services/printer_file_guard.py` answers whether a file may be deleted now, for every door: the file browser's delete, `clear-sdcard`, `timelapse/delete-oldest`, the tidy-up after a timelapse attach, the post-print cleanup and the dispatcher's own deletions. The file a loaded job reads — RUNNING, PAUSE, PREPARE or SLICING, matched by name on both storages, with its `/cache` working copies — and another dispatch's expected print are kept; a matching hash is no exception, because the next print of the same 3MF has the same name and bytes. Permission needs a fresh connected observation: a disconnected, silent or unreported printer is not idle, and `is_print_active` (False for those) is no gate. A bulk deletion needs a positively idle printer with no expected print and stops at the first step after that changes. No caller may skip the fresh observation, the dispatcher included: a cached IDLE proves nothing about a print started since the connection dropped, and an earlier reconnect is not an observation made after the lane wait; a job waits, bounded, for a reconnecting printer to report (`_FileGate.wait_until_observed`) and then asks like everybody else. The dispatcher's `_FileGate` is one object per run for every delete AND for the upload itself — writing over a name destroys the file under it — and it REMEMBERS a refusal: the refused command answers the same "failed" as a network error and the state may look safe again by the next read, so a remembered refusal, or a file the internal listing found and the printer did not delete (`clear_internal_by_name`), ends the upload (`UploadFailed`) before its first byte. The check is the transport's `may_run`: asked after the wait for the printer's file channel, immediately before the command — a place in the lane is no right to delete. Results are read: only `DeleteResult.DELETED` is a removal — an answer of nothing is not one. The post-print cleanup has a cooperative 120 s deadline (`_cleanup_may_run`), never `asyncio.wait_for`, which cancels the coroutine and walks away from a step still running on the lane. `tests/unit/test_printer_deletes_ask_the_file_guard.py` fails a deletion without a gate. Not covered: a `DELE` the firmware already accepted is not recalled. A firmware upload is the same touch of the printer's storage: `firmware_update.upload_refusal` is `wide_refusal`, asked at prepare, again after the file was fetched from Bambu Lab, and through `may_run` before the first byte (single and bulk), and `print_scheduler._is_printer_idle` answers no while `firmware_update.upload_in_progress`. Vault: `40-invariants/inv-printer-file-delete-asks-the-guard.md`.

## An archive's video has one registry, one publication seam and one owner (G10 C, m237)

`archive_media_assets` is the registry of an archive's videos and `services/archive_media.py` its only writer (`tests/unit/test_archive_media_has_one_writer.py`); `PrintArchive.timelapse_path` is the projection of the primary row, reconciled by the seam when they disagree. Bytes never go over the live file: a writer stages `.<uuid>.part` beside the target and `publish_primary` makes it the video in one transaction — target identity and storage epoch rechecked, `expected_token` (`primary_token`, the video the caller started from — "no video" has a revision too, `none:<highest revision>`, kept up by the `retired` tombstone every removal leaves, so the emptiness after attach-then-remove is not the emptiness before it; no default — whoever starts captures identity, epoch and token BEFORE its first long I/O, and `attach_timelapse` captures on entry what a caller left out) compared, a manual door's frozen authority and rights asked again through `domain_authority.guard` as the write scope's `first`, the scan's run proof (`may_run`) asked again immediately before the bytes take their name, the printer recording (`RemoteSource`: printer `connector_identity` + storage + normalised path) claimed through a unique index, so one recording belongs to one archive (`source_claimed`) — and the previous file is unlinked only AFTER the commit, only when no other row still shows it and only when its stored path stays inside DATA_DIR (`contained`; a pointer that escapes is left alone); a refusal removes the staged file and changes nothing. ⚠️ The bytes take their name BEFORE the commit, so a publication's file never takes the name the archive's pointer already holds — not even when that file is gone (`_free_name(…, shown)`, G10 D review): a reader of the pointer meets the committed version's file or nothing, never uncommitted bytes under the old version's name. A claim outlives the video made from it: replacing a printer video (conversion, layer video, upload, reprint reset) leaves a `receipt` row holding the claim and the hash of the DOWNLOADED bytes, and only the operator's removal or the archive's deletion releases it. `remove_primary` is the same seam; a writer already inside a transaction (the reprint reset) uses `detach_primary_in`, which never commits — the caller unlinks through `unlink_released` after its own commit. A conversion converts only the video the archive shows on entry (its own publication, handed in as `started_from`) and publishes with that token, so one queued for replaced bytes does not start and one that ends after a replace or a delete is refused. Every hard delete of archives calls `forget_archives` for exactly the ids it removed (the trash sweep: `DELETE … RETURNING`). The automatic attach needs a TRUSTED boundary: the recordings on the printer before the print recorded — one entry per medium and path (`timelapse_files.recording_key`), never a bare name — kept in memory (with its owner: archive incarnation + process epoch) and in `extra_data["timelapse_baseline"]` (`services/timelapse_baseline.py` — taken at start, or `late` for a print found running, when what exists then is not new). A stored record is ADDRESSED — archive incarnation, printer `connector_identity`, the durable storage epoch (the Settings row a restore rotates, never `queue_sources.current_epoch()`, which starts over at every boot) — and the scan reads it only at that address; a reprint's reset drops it (`forget_in`); a capture overtaken by a restore or a newer run is discarded; a later capture never destroys a trusted one (`save` → `_keeps`), and a late capture first takes back what the archive already keeps. The capture carries its caller's run proof (`owns_start`, the recovery's `recovery_current`) through every wait, and memory is written only AFTER the archive kept the list — a list the archive refused is nobody's boundary. What each medium said decides about ITS recordings (`baseline_media` / `media_of`): the listing stops at the card when the card has videos, so a recording on a medium that was not asked or did not answer at the capture is no candidate. No boundary, or one read off storage that did not answer, attaches nothing — never a list taken at completion, never a name that resembles the print — and `may_run` stops the scan of a superseded run before the listing, the download, the attach, inside the publication and before the printer delete; a printer without an identity is claimable by nobody and gets no automatic attach. A recording is deleted from the printer only after ITS attach succeeded and only as the very bytes of a LIVE copy: `remove_recording_after_attach` pins the primary row that claims it, shown by its archive with its file on disk (`archive_media.pin_live_copy` — a receipt is history and authorises nothing; the pin is registered and the copy is then looked at AGAIN, so a removal that won while it was being found leaves no pin; every door that takes the copy away revokes it — `_retire`, `forget_archives` for a hard delete, `_unlink` by path after the commit — and `holds()` also asks the disk at the moment of the command), and the transport reads, compares and deletes in ONE occupancy of the printer's file lane (`delete_verified`: `ready` → read → `verify` → the file guard and the caller's proof → the command); a transport without it deletes nothing. `services/archive_media_runtime.py` owns every such writer (attach with its staging, publish, remove, conversion): refused once admission is closed (`restoring`), not detached by a cancelled caller — who is held until the work ends, because the work uses the caller's session — and waited for, never cancelled, by a restore (409 when still running) and, bounded, by shutdown; only lifespan startup reopens admission. The editor's ffmpeg children are owned since G10 E, the layer stitch's since G10 F. Vault: `40-invariants/inv-archive-video-one-seam-one-owner.md`.

## An edit of an archive's video is a job, and every ffmpeg / ffprobe of the editor is an owned child (G10 E)

`services/media_child.run` is the one way the editor starts a child process: a watcher thread owns the `Popen` from before its spawn to its reap (a thread, not an asyncio subprocess — Windows `--reload` has none), registered in `media_child._live` BEFORE the thread starts, so a cancel that lands during the spawn ends a child that exists and never leaves an orphan. A hard limit, an idle limit (no `-progress` line), a stop event and the caller's cancellation all end it the same way — terminate, a grace, kill, then WAIT for the reap; a child whose end was not seen is `unreaped` and stays counted by `media_child.live()`, which is what a restore asks. The parent log carries a start and one outcome with elapsed time and a correlation id, never a command line or a path; stderr is drained to a bounded tail. `services/timelapse_editor.py` is the job runtime: `reserve` takes the place synchronously with the count (one edit per archive incarnation + `primary_token`, 409 otherwise); the admitted video is PINNED into the job's directory when the place is prepared (`_pin_source`: a hard link, a checked copy where links are not possible) and compared with the file identity captured when the archive was read — ffmpeg reads the pin, so another video put under the same name, size and time later is never encoded, and one swapped in before the pin refuses the edit `source_changed`; the music is streamed from the RAW request body into the job's own directory under `DATA_DIR/timelapse-edits/` — never a multipart form, which Starlette writes whole to the system temp before any handler runs — counted and capped; one encoder runs at a time for the WHOLE process, shared with the layer stitch (`services/encoder_slot.py`: the check and the taking are one synchronous step, waiters first come first served, a stopped or cancelled waiter leaves the queue) — never a per-runtime turn computed from a registry, which let an edit delayed in its preparation start a second encoder; a `live_authority` handle watches the caller while it runs. The result is published only through `archive_media`: *replace* is `publish_primary` with the token captured at admission, *save as new* is `publish_variant` (a `variant` row and a name of its own; the pointer is not touched), both with the caller's authority asked again inside the transaction — a video replaced or removed meanwhile refuses the result `source_changed`. A cancel is honoured or refused, never both: the seam asks the job once more under its own locks, last immediately before the bytes take their name (`may_run` → `still_wanted`, which sets `EditJob.no_return` in the same synchronous step), an accepted cancel publishes nothing, and from that step on the door answers 409 `cancel_too_late`. ⚠️ The request of before this unit was a FORM with the same field names: read as the new request it has no query parameters, so every field would take a default — it is refused 415 `legacy_request` before anything is read, and the default of `save_mode` is the one that keeps the original (`new`). Progress stops below 1.0 until the publication committed; `cancelled` is said only after the child was reaped and the job's files removed; an unreaped child leaves the job `process_unreaped` with its staged output untouched. The encoder writes into the job's own directory whenever that shares a volume with the video (`_staging_place`) — the scratch tree is outside every backup, so a backup taken during a long encode meets no file that changes under it — and beside the video only when the archive lives on another volume; that file is then named in the job directory before the encoder may create it, and startup's `clean_scratch` removes a marked directory together with exactly that file — by the marker, never by age or a look-alike name. Restore and shutdown call `timelapse_edit_runtime.quiesce` BEFORE `archive_media_runtime.quiesce`; only lifespan startup reopens. `ffprobe_beside` changes the FILE's name only — a replace over the whole path also rewrote a folder named `ffmpeg-…`. Probes and thumbnail strips are bounded (10 s, 30 s per strip), shared per file and limited to two at once. ⚠️ In the tests every session shares one connection: a status request made while a job publishes releases the publication's savepoint, so a test waits for the job's own `done` event instead of polling through it. Vault: `40-invariants/inv-video-edit-is-an-owned-job.md`.

## A layer recording's frames have one owner, named in their own directory (G10 F)

A session of `services/layer_timelapse.py` is a UUID, never the clock, and its directory `timelapse_frames/<printer>/<uuid>/` carries a manifest (`session.json`) the session writes: its id, printer, archive and STATE — `active`, `finalizing` (written BEFORE the stitch starts) or `retained`. A frame being written and the encoder reading the frames both hold the session (`_hold` / `_release`); `cleanup` asked meanwhile runs when the last holder has ended, and a frame that arrives after a cancel or a detach is not written. ⚠️ A disk write is owned until its THREAD ends, not until the coroutine that asked for it does (`_owned_io`: the hold and the count in `_io` are released by a callback on the future, never by the caller's `finally`) — a cancelled capture, or one whose session was cancelled or detached meanwhile, used to let a restore's drain succeed over a thread still writing a JPEG. A stitch whose ffmpeg was not reaped pins its session in `_pinned_sessions` for the life of the process, and that registry is read by EVERY path that could free the frames or the output: `cleanup`, the retention bound, the sweep and the drain (the stitch that set the pin used to run the bound itself and delete the frames). The stitch takes the process's one encoder (`encoder_slot`, shared with the editor). The stitch is a `media_child` child: two encoder threads, lookahead 10, a hard limit that grows with the frames (`stitch_limit`: 300 s + 0.5 s per frame, 3600 s at most), an idle limit on `-progress`, the source resolution kept (OD-6), and its result probed before it counts. A stitch that fails, is stopped or errors RETAINS its frames and removes its own unfinished output; the caller (`main._background_layer_timelapse`) asks `finish_session(keep_frames=True)`, attaches the video as a FILE (`ArchiveService.attach_timelapse_file` — moved on the same volume, hashed in chunks, never `read_bytes`) through the publication seam with the token captured before the stitch, and only then calls `cleanup`; a refused publication calls `retain`. A print that failed or was cancelled discards its frames. Retained frames are bounded — 24 h and 2 GiB over all of them, oldest first (`apply_retention`) — and the bound is applied at EVERY step into `retained` (`retain` itself, a refused publication after a good stitch included; blocking, so callers on the loop hand it to a thread) and again every hour by `start_janitor`, cancelled by `stop_janitor` at shutdown; capture stops for a session, with one warning, at 10 GiB of frames being recorded or at the volume's reserve. The startup janitor (`sweep_orphaned_frames`) decides by MANIFEST: an owned directory no live session has becomes `retained` (interrupted) and then falls under those bounds; a directory in the old timestamp shape holding nothing but frames is adopted the same way; a stitched output named for a session that no longer lives is removed; anything else — no manifest, a manifest naming another session, a plain file, a link — is left alone and never entered. Never decide by the age of a directory that is not provably ours. `layer_timelapse.quiesce` closes capture, stops every stitch and proves writers and encoders ended — no stitch being finalised, no write in `_io`, no pinned session; restore (409 otherwise) and shutdown call it before the edit runtime and the media seam, and only lifespan startup reopens. The camera side is unchanged: frames come from the live view's buffer or the capture runtime, and no recorder stops the shared producer. Vault: `40-invariants/inv-layer-frames-have-one-owner.md`.

## A finish photo is written where its archive is at the moment of the write, and a refused one is removed (G10 G)

Every writer of a finish photo — the frame banked at the last layer, the live view's buffer, the external camera's grab, the fresh built-in capture and the last frame of the printer's own timelapse — asks `services/finish_photo_store.py` immediately before it writes: `photos_dir_at_write` reads the archive row again and answers its folder (`photos_dir_for`) only while it is still the very archive the terminal was for (`recovery_identity` — SQLite hands a deleted archive's id to the next one), and `save_frame` also asks the terminal's own proof that the printer has not gone on to another print. A folder worked out from a row read before the waits is never written to — the built-in camera included: `camera.capture_finish_frame` gives a FRAME, never a file, and takes no folder, because the capture can take half a minute and a 3MF attached meanwhile moves the archive's folder. The store keeps the exact address of every file it wrote until that file is settled (`_own`: `confirm` after the attach committed, `discard` otherwise): a refused photo is removed where it WAS written, never looked for through the archive row, which may by then be another archive under the same id. A commit that fails while attaching a photo has an unknown outcome: `settle_uncertain` reads the archive afresh, keeps the photo when the archive lists it and removes it when it does not; when the archive cannot be read nothing is removed on a guess. `_capture_finish_photo_from_timelapse` takes the same proof (`may_run`): asked on every poll and after the extraction, and the stored video pointer is joined only through `archive_media.contained`. ⚠️ No finish photo code sends a printer command: what triggers a capture and from which source is unchanged, and `tests/unit/test_finish_photo_store.py` scans the three functions and the store for command verbs (owner decision 2026-09-14: no motion for the sake of a photo; upstream's Z-raise / park leg is rejected). The frontend's timelapse viewer and editor take their video box from `components/timelapse/videoBox.ts` — `w-full`, a height cap and `object-contain` — so a portrait recording is letterboxed inside the window instead of pushing the controls below the fold; the caps were measured in a real browser, never give the video only `w-full` again. Vault: `40-invariants/inv-finish-photo-written-at-the-write.md`.
