# Invariants: Part renders, previews and labels

Full text of the rules that [`CLAUDE.md`](../../../CLAUDE.md) keeps in short form, with the reasons and the history behind them. `Vault:` pointers name notes in the maintainer's private knowledge base; everything a contributor needs is here.

## A part-render attempt is over only when its process tree is proven gone (E3)

The disposable `part_render` is the only reader of a library file for rendering: it opens, hashes and streams the file and starts Node in its own process group / Job Object; main and `part_render_service` never `stat`, `resolve` or open the path. Every process of an attempt is recorded by its PARENT — `<name>.launch` (a one-off token the parent also puts on the child's command line, `launch_arg`) before the spawn, `<name>.pid` (`pid` + start + the boot it ran in) before the child gets any input (`services/part_render_tree.py`) — and the worker answers a run only after `PreviewProcess.stop()` and `tree_gone` prove the tree gone. Main's one slot (`PartRenderRuntime.render`, an `asyncio.Lock`) is held through the reply, the cancel and, failing that, the retire with the same proof (`strict=True`) over every attempt in the worker's staging — which also covers a tree orphaned when the worker itself died. An unproven tree, or a start whose cleanup proved nothing (`SpawnUnproven`), makes the runtime `ownership_uncertain` until a restart and no replacement worker starts: a retry never runs beside a reader still hung on a NAS. The parent log says why a proof failed (`tree_unproven`: the record, the check, the pid and its psutil status — never a command line or a path). A worker that dies inside an attempt's spawn window leaves a launch without its record (measured on macOS, 2026-10-10): main's strict proof of THIS run (`tree_unproven(strict=True, generation=…)`) ends it by its token once its parent is proven ended in the same walk — the worker itself proven ended by its records first (`worker_records_unproven`, before any attempt) — killing the parent's token holders (a fork caught before its exec) before the launch's own, under the same right to signal as below; a fully recorded attempt is still proven by its records alone, with no process-table scan. A launch file that cannot be read is no token, and any error inside `retire`'s proof is no proof: `ownership_uncertain` before it returns, every record kept, restore refused, the log naming only the stage and the error's type. Only a worker that never received its bootstrap stays outside the proof — a limit of the proof, not a refusal: it can launch nothing, and EOF is no proof that it ended; an attempt that needs it as a parent is refused. An EARLIER run is proven over by its records — never by a bare negative scan of the process table (a child born as its parent exits slips past any scan): a generation records its owner (main), its worker guardian and the worker beside its attempts, and `part_render_tree.generation_gone` needs that main dead (never killed — a live one is another main), then every recorded process ended, killed if need be, PARENTS FIRST. A launch without its record is ENDED, never trusted to read EOF: once its parent is positively proven dead nothing new can take its token, so every holder of it is killed and waited for until a scan finds none — and of the parent's token too, because a fork caught before its exec still runs the parent's command line; an unreadable token is no proof. A command line is public, so a holder positively of another user (the uid POSIX shows for every process — one only when real, effective and saved agree, since none of ours changes uid, so a setuid `sudo` of the same user is someone else's; the user name where Windows shows it) is a stranger that read the token, never signalled and never able to keep the run unproven — and carrying the token is no authority to signal: a holder is killed only when its user is READ and IS the run's owner, while a hidden identity, or a run whose owner names none, keeps the run unproven and the holder untouched. Only such a POSITIVE observation excludes a process — psutil answers `None` for what it may not read, and `None` is not absence: a process that may be ours and whose command line cannot be read keeps the run unproven (on Windows a process running another image, or started by the kernel, is positively not ours — the image name and the creator are shown for every process). A record names its boot: one of another boot has ended and its pid is never signalled, and a run whose owner names another boot is over whole, whatever a power cut left of its files — a persisted boot counts only in its platform's format (what the reader writes: a UUID, a `bootid-<DWORD>`), any other text is no boot at all. A pid and a start identify a process only within one boot, so a record matching a live process is acted on only when its boot and this one are both known and equal — an unknown boot signals nothing, on every platform; `tree_gone`'s records are this run's, so this boot's by construction. The one process outside every token is main's own fork caught before it executes the worker guardian, which can only read EOF where its bootstrap should be and exit. An error in that proof closes admission and restore; without a scheduler, restore asks for a completed proof (`earlier_proven`). A proven earlier run's staging is removed. A restore asks `scheduler.stop("restore")` first — one shared stop, its proven answer — and refuses (409) without the proof; that stop joins the runtime's own `stop()` (also one shared stop), because the monitor retires a dead worker OUTSIDE the slot: the answer waits for that proof to finish, and no replacement worker starts — rendering stays stopped until the process restarts. `plate_renders` / `plate_render_objects` / `part-renders/` have one writer, `services/part_renders.py` (guard test); every transition is a CAS on the full key and the scheduler's generation. ⚠️ What an untrusted plate makes the child hold is bounded: a top/pick image is measured from its PNG header (PNG only) before it is decoded, the marker scan keeps only the selected ids. Vault: `40-invariants/inv-part-render-attempt-proven-over.md`.

## A part render runs our verified bundle over data, nothing else

Node runs `backend/app/data/part_render/part-render.mjs` only after `part_render_node.verify_bundle` matched it to its manifest (a mismatch is `bundle_mismatch`, no render); `node_command` disables code generation from strings and turns on Node's permission model with read access to the bundle alone — no file writes, no child processes — and `node_env` passes an allowlist environment. The manifest records the dependency graph and `test_part_render_bundle.py` fails a new import or a module from outside the allowed directories, so no network or code-loading code slips in; vitest rebuilds the bundle from source byte for byte. What Node answers is accepted only when every entry is exactly a requested id of this renderer version with exactly its valid PNG (`_check`, then publication); anything else is `invalid_output` and nothing is published. JIT stays on deliberately (owner, 2026-10-07); there is no browser in the render path. A change to `frontend/src/part-render/*` ships a rebuilt bundle in the same commit, and a change to a render input is first a `RENDERER_VERSION` decision (`test_renderer_inputs_digest.py`). Vault: `40-invariants/inv-part-render-runs-our-code-on-data.md`.

## A platform's Node is the newest LTS line that publishes an official signed build for it; the pin script is the only writer of the pin and the golden

`render_runtime.json` files lines (`lines.<major>`: version + end of life) and every platform names its line — 24 for linux/darwin x64 + arm64 and win-x64, 22 for `linux-armv7l` (32-bit armhf: the userland's SOABI triplet and a glibc interpreter decide, not `uname`; every recognised machine meets one `PLATFORMS` check, so a line that left it is `UnsupportedPlatform`, exit 3). `scripts/pin_render_runtime.py` takes hashes only from a `SHASUMS256.txt.asc` a vendored release key signed, takes `--line` only for a published LTS of that line, refuses a line past its end of life, and writes manifest + golden only after every pinned version rendered the same PNGs (a version that changes pixels is a `RENDERER_VERSION` decision, never a re-golden); `golden.json` lists exactly the pinned versions. A new major line is never pinned automatically; `--check` exits 2 for an action (a newer patch, an ended line) and 3 for notices only (a new LTS line, a line ending within 90 days), and only an action holds a release. `node-pin.yml` makes the weekly pin in a job with a read-only token, no stored credentials and only the probe's packages; a package-free job re-checks it (`--verify --expect <check.json> --base-golden`: the versions the check chose — no downgrade —, the signed sums, the base golden, nothing but the two pin files changed) before it pushes a `chore/node-pin-*` branch, and fixes ONE candidate SHA that every job of `part-render-smoke.yml` (five native runners, each checking the platform it promises, + armv7 under QEMU) checks out and the issue names — a branch that moved after the smoke is never called tested; the issue lives only while there is an action. Provisioning removes from `<runtime>/node/` only a platform that left `PLATFORMS` — never a pinned one, because a checkout mounted into a container holds the host's Node. A native install (`core/install_kind`) that starts with `runtime_missing` provisions once in the background from the process's start (`part_render_scheduler.start_part_render` → `runtime.start_provisioning()`, reason `runtime_provisioning`) — never Docker / the Windows installer, never a runtime a test starts on its own; startup and the Settings update both go through `render_runtime_child.run_provision`, which owns a `Popen` through a watcher thread (no asyncio subprocess: Windows `--reload` has none), keeps a bounded, redacted stderr tail, logs one outcome with its elapsed time, and on a cancel or timeout waits for the child to the end. A provision holds its platform's lock (`runtime/node/.<key>.lock`) and under it reclaims the downloads and staging dead runs of that platform left — never another platform's, the `.old` backup or the lock; what the OS still holds is named apart, never called removed. The reclaim runs under the lock even when the pin is already in place; only when the lock file cannot even be opened (no write access — a runtime directory a `sudo` run left root-owned) does a pin in place still succeed, with nothing reclaimed. Vault: `40-invariants/inv-node-pin-newest-line-with-official-build.md`, `60-specs/part-render-startup-provisioning-spec.md`.

## A render result is an immutable attempt directory the database points at

`part_renders.publish` renames a finished attempt into a NEW name under `part-renders/` and switches the plate row's `result_dir` to it in the same transaction, under the scheduler generation's CAS; a CAS that matches nothing removes the new directory, an unknown commit removes nothing, and the previous directory goes only after the commit — readers see the old picture until the new one is in. Only directories proven ownerless are removed (`reconcile` at start-up, `gc_due` → `gc_remove`). Rejected: a stable per-plate directory overwritten in place — `os.replace` onto a non-empty directory fails, and a crash between rename and commit left a directory no reconcile owned. `part-renders/` is the one `DATA_DIR` root deliberately outside backups (derived; re-rendered after a restore). Vault: `40-invariants/inv-part-render-attempt-dir-immutable.md`.

## A single object's model area is BambuStudio's first-layer outline, found by name (E7 acceptance, 2026-10-12)

`Metadata/plate_N.json` files `bbox_objects[].id` under the PrintObject's id — a counter apart from slice_info's `identify_id`, so never look the record up by `identify_id` (it matched on no real file, and `model` was dead on every one) — and its `bbox` is the FIRST LAYER's outline (`Plater::priv::generate_first_layer_bbox`), not the object's extent. So the record is the plate's one entry beside the `wipe_tower` and only under the object's name (`part_render_fallback.model_bbox`), and what is compared with it is the FIRST selected layer in G-code order — the lowest for a plate printed layer by layer, the only kind `model` reaches (`part-render/select.ts` → `Selection.firstLayer`, `job.ts`); what lies above it is deliberately not bounded (a `job.test.ts` case pins that): a part overhanging its footprint is proven, a typed purge line on the first layer beside it is not (spec §5.3, condition 3). A fixture whose ids agree hides both — `single_object_3mf` is in BambuStudio's shape. Vault: `40-invariants/inv-plate-json-bbox-is-the-first-layer.md`.

## A STEP thumbnail: OCP only in a disposable child, the picture published only by main (STEP thumbnails, 2026-10-19)

OCP is imported by one process alone — `services/step_thumbnail.py`, the conversion child the preview service starts through the worker guardian after the bundle is activated: one STEP in, one bounded STL and a closed `result.json` out; a model partial in any way is `render_failed`, never a picture of part of it. The PNG is drawn by the ordinary mesh renderer child, and only main publishes it, under the bound-publication rule (`40-invariants/inv-preview-main-only-publication.md`). `step_runtime` itself never imports OCP: it is stdlib-only (Dockerfile, install.sh and the Windows build run it before the app), and its one catalog — `data/step_runtime_manifest.json` + `step_runtime_closure.json` — has one writer, `scripts/pin_step_runtime.py`; a `candidate` pin installs only with `--allow-candidate`, which no official build passes. The bundle lives under `<app_dir>/runtime/step-preview/` — not DATA_DIR, not in backups. The queue is `services/library_preview_jobs.py` in main: volatile (no table, no replay after a restart), one execution per file and source fingerprint shared by every actor's receipt, its own budgets; in the one preview slot (`services/preview_arbiter.py`) STEP is the lowest class, and only a sliced attempt preempts an active one. Who may ask is closed (`test_step_thumbnail_doors_are_closed.py`): the shared upload and ZIP door through `_queue_step_thumbnail`, and the explicit button — MakerWorld, the archive, the printer's files, the Virtual Printer, calibration and the scanner never do. `calib_geometry.step_to_stl` is a separate calibration path: never a global ban on STEP in the code. Vault: `40-invariants/inv-step-cad-only-in-the-child.md`.

## The STEP component's copyleft sources ship with every release (2026-10-19)

The Docker image and the Windows installer carry the CAD component, and its parts under a licence that asks for their source — OCCT, LibRaw, FreeImage, on Linux libgomp — get that source from BamDude itself. `scripts/step_preview_sources.py` is the one place that decides what is copyleft (`COPYLEFT` over a part's chosen `terms`, else its `licence`; `test_step_runtime_notices.py` imports it) and packs `bamdude-step-preview-sources-<closure_sha256[:12]>.tar` from identities `step_runtime_notices.json` pins. ⚠️ Complete source is the upstream AND what controlled the build (Codex SRC-R1): a source RPM by the SHA-256 of a copy whose vendor signature was checked (it carries its spec and patches); an archive by its SHA-256 plus, for every conda-forge package in `packages`, that exact package's recipe read out of it by its SHA-256 (meta.yaml or recipe.yaml, build scripts, licences — refused when a patch they apply is missing); OCCT by its git commit plus the `built_by` build system's tree that patched and compiled it. A copyleft part with no build record is refused. Other bytes are refused and nothing is packed; the same sources give the same bundle, byte for byte (Python 3.14 for the stdlib zstd). `step-preview-sources.yml` attaches it to every tag's release, and the Docker push and the installer's attachment `needs` a job that runs `verify-release` — this closure's bundle, published, fully uploaded, every pinned identity in it — so a failed sources run holds both; the manual `:dev` publish and `docker-publish.sh` run `verify-published` (this closure's bundle on a published release) before they build. A closure an earlier release already carries is taken from that release, verified (`collect --reuse-from`), before upstream is asked: the upstream of an older pin may be gone for good (EPEL keeps only a package's newest build). The notices README that ships names the bundle and offers the source on request for three years; a repin that changes the closure fails `test_step_preview_sources.py` until the README names the new bundle and any new copyleft source is pinned. ⚠️ Never delete these assets: `cleanup-betas.sh` keeps a beta's GitHub release unless a PUBLIC copy of the same bytes stays (a published, not draft, release; uploaded; the same digest — never a name alone). Vault: `40-invariants/inv-step-copyleft-sources-ship-with-releases.md`.

## Server-side plate thumbnails (best-effort)

`services/plate_thumbnail.py` fills missing `Metadata/plate_N.png` in sliced 3MFs. **Any failure returns the input bytes unchanged — must never fail the slice.** Layered AFTER `library_3mf_preview.inject_source_stl_preview` (higher-fidelity plate 1 from STL); the checker skips plate 1 and only fills blanks (STEP/STP, preview-less 3MF, plates 2..N). Don't reorder the two passes.

## Labels are data, not layout code

`label_templates` / `label_sheets` (m146) hold a design as a list of mm-positioned boxes; one walk (`label_canvas.draw_template`) feeds two backends — PDF and a 1-bit raster. Editor lives in Settings → Filament → Marking and NOWHERE else. Direct-to-device printing (m147, `label_devices`/`label_jobs`) has the server hold a queue a desktop bridge polls. ⚠️ The template is the truth and the cassette is the gate: a design is printed at its own size or refused, never scaled — fractional scaling of 1-bit destroys bar ratios silently. ⚠️ An un-adopted device is frozen by design. The designs and sheets BamDude ships (`builtin_key`) are ordinary rows: editable and deletable (owner, confirmed 2026-11-16). Full detail: vault `20-systems/label-templates` + `20-systems/label-devices`.

## Every label draw passes one gate and runs on its own two workers

`services/label_gate.py` is the door every route that draws a label goes through (save, preview, print, device queue, PNG export): it asks the bounds in `label_template.py` (`design_problems` / `sheet_problems` / `picture_problems` / `colour_picture_problems` — functions, not `Field` limits, so a stored out-of-bounds row still lists and is refused at print) BEFORE anything is drawn, then draws on a dedicated two-worker executor with a ceiling on waiting plus drawing (a translated 503 after it) — never on the event loop and never on the loop's shared thread pool, which uploads and the print gates also use. "The design fits the cell" is ONE function, `label_template.fits_within`; the dialog reads the server's answer (`fitting_design_ids`) and never computes its own. A colour picture of a label (dialog preview, the editor's preview of a driver design, PNG export) is the PDF backend's own page rasterised by `services/label_picture.py` — no third drawing backend, pixel size = the design's mm × dpi, never scaled; that module and the preview child's `services/pdf_thumbnail.py` are the only two importers of `pypdfium2` (a guard test names them): the first reads PDFs we generate, the second untrusted uploads, and only inside the disposable child. Vault: `20-systems/label-templates.md`.
